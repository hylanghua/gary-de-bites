Aaron Levie：AI 就业预测正在落地，「Agent 操作员」和网络安全成为真实的新职位类别

Aaron Levie（Box CEO）在 X 发帖分析当前 AI 就业市场的变化：过去两年里被广泛讨论的「AI 催生新职位」预测，正在从概念变成实际招聘中的职位名称。他点名了两个特别值得关注的方向：一是「Agent 操作员」（agent operator，负责监管、校正和管理 AI Agent 工作流的人），二是网络安全相关岗位，后者的需求增长直接来自 AI 被大量使用后攻防面的扩大。

Agent 操作员这个角色的出现有其逻辑：当 Agent 系统开始在企业内部大量运行，总要有人负责理解它们在做什么、出错时如何介入、如何定义边界，这个角色介于传统运维和产品经理之间，目前没有对应的教育体系，全靠实践摸索。「Agent 操作员」不是 AI 未来的职位，是 2026 年秋天企业里正在雇佣的真实岗位。

AI 方向观点

Amjad Masad（Replit CEO）：我不认为我们达到了 AGI，但当前的 AI 和 AGI 功能上无法区分

Amjad Masad 在 X 写道：「我不认为我们已经到了 AGI，但我们拥有的和 AGI 在功能上无法区分。」这句话的结构很耐人寻味——他不打算在定义上辩论，但又清楚地说明了他感受到的现实：边界已经模糊到没有意义。他的背景不是政策研究者，而是每天看着 Replit 用户用 AI 构建真实软件的人，这个观察来自实操端，不是理论端。

这和 Jensen Huang 上周宣称「AGI 已经到来」形成了有趣的对比：Huang 给了一个肯定判断，Masad 给了一个认知论的规避——「无法区分」比「已达到」更难被反驳，也更能描述日常体感。如果「功能上等同」就足以驱动决策，那么继续争论 AGI 定义的意义在哪里，这才是 Masad 这句话真正在问的。

Aaron Levie（Box CEO）：要为量级能力提升构建，不要为当前状态优化

Aaron Levie 发帖说：能力量级提升（orders of magnitude improvement）才是正确的建设视野。他的意思是：今天拿到一个工具，如果只按它当前性能做产品规划，会严重低估六个月后的实际情况。正确的方式是以「能力将会量级提升」为假设前提来设计架构，这样才不会在 scaling 到来时反复重构。

这个判断来自他在 Box 里实际观察到的节奏：去年用的 Agent 在今年已经不是同一个量级的工具。对 PM 的含义是：产品路线图的「长期」现在是 18 个月，「中期」是 6 个月，「短期」是 6 周。为下一个量级设计的架构选择，和为当前量级优化的架构选择，是完全不同的决策树。「为你没有的能力设计」听起来是工程浪费，但在当前的 AI 节奏里，它是避免永远在追的唯一方式。

X @levie

Amanda Askell（Anthropic 研究员）：给自主 AI 一个可以主动联系人类的专用邮件地址

Amanda Askell 在 X 写道：「如果给自主 AI 模型设立一个专用邮件地址，让它们在遇到问题时可以主动联系——这会是一件很酷的事情。」这个设想背后是一个具体的问题：当前的 Agent 系统在遇到边界情况时，要么卡住、要么继续执行（可能出错），缺少一个结构化的「我不确定，请人来确认」的通路。邮件地址是一种极其简单的实现——不需要任何复杂基础设施，只需要 Agent 知道有这个地址、知道什么情况下可以用。

这和 Mollick 上期提到的「暮光工厂」框架有直接共鸣，但走的是另一个方向：Mollick 的框架是在 Agent 系统内部设立协调者；Askell 的想法是给 Agent 一个向外部发信号的直接通路，而不是只能在内部路由。让 Agent 能主动发出「我需要帮助」的信号，比让人类不断检查 Agent 状态，可能是更现实的监督架构。

产品与商业

Roman Ugarte：从零到 Grok Bot 上线只用了七周，「同事即 AI」不是口号而是设计原则

Roman Ugarte 在 Lenny's Podcast 详述了 Grok Bot 的完整诞生过程。核心时间线：第一行代码到内部可用产品用了四周，公开发布再用了三周。团队做的第一个关键决定是从头构建，而不是把 Grok Bot 功能叠加到 Cursor 上——这个决定保住了产品的简洁性。第二个决定是在产品上线初期亲自给将近 300 名用户做 onboarding（用户引导），而不是把这件事自动化掉，目的是直接感受用户真实的困惑点在哪里。

「同事即 AI」（colleague-pilled）是 Grok Bot 的核心产品框架。不是聊天机器人，不是工作流自动化工具，而是一位有持久记忆、能登录你用的软件、能自主完成任务再来告知你的同事。用户把任务交给 Bot 的方式和交给真人同事一样——发消息，不需要配置自动化规则。Ugarte 指出，Bot 的名字和个性设计会直接影响使用行为：用户对「一位叫 Holly 的客服同事」的期待和对「客服模块」完全不同，会更自然地给 Holly 发复杂的任务。

他在访谈中反复强调的一个判断值得记录：「一个能完成 100% 工作的 AI 和完成 90% 工作的 AI，感受上是截然不同的类别。」这不只是精度问题，而是信任模型的问题——90% 的结果要求用户持续监督，100% 的结果让用户可以真正交出去。Grok Bot 的竞争优势不是技术参数，而是「用户愿意把什么类型的任务交出去」这个信任阈值——这是一个产品判断，不是一个模型判断。

Guillermo Rauch（Vercel CEO）：软件工厂需要高质量视频录制，agent-browser 现在能做到了

Guillermo Rauch 在 X 发帖说：软件工厂（software factory，指 Agent 自主运行的完整开发流水线）需要高质量的视频录制能力，agent-browser 提供了这个能力。这背后的逻辑是：当 Agent 在浏览器里执行任务，人类需要有办法回放、审查、调试 Agent 的行为过程，就像代码有 Git 历史，Agent 的视觉操作记录也需要可溯源。

这个功能看起来是工程细节，但对于真正把 Agent 投入生产环境的团队来说，「能看到 Agent 到底做了什么」是信任基础。没有操作录制的 Agent 系统就像没有日志的服务器，出问题时没有任何信号可以分析。给 Agent 的操作加上可回放的视觉记录，是把 Agent 系统从「跑起来就算」推向「可审计、可改进」的关键一步。

Garry Tan（YC President）：RFS 只是 YC 想聊的话题，不是在告诉你该做什么

Garry Tan 对 YC Request for Startups（RFS，YC 公开发布的「我们想投资的创业方向」列表）的定性做了一次澄清：RFS 是对话的起点，是 YC 合伙人在某个时刻觉得有趣的领域，不是 YC 的投资决策标准，也不是对创业者「你应该做这个」的指令。他的意思是，很多创业者会对着 RFS 选赛道，但这本质上是误解了 RFS 的功能。

人文与哲学

Kieran Klaassen（Cora / Every.to）：AI 让工厂在黑暗中运转，别让它把你头脑里的灯也熄灭

Kieran Klaassen（Every.to 旗下邮件产品 Cora 的总经理）在今天发表了一篇直接触碰自身经验的文章。开篇他承认：他现在发布产品的速度是历史最高，但他的大脑感觉变软了。过去一年他专注于「把自己从系统中路由掉」——一旦找到 AI 可以替代的环节，就让 AI 接管，这是他所说的「复合工程」（Compound Engineering）的本质。结果是产品变好了，但他自己作为判断者的能力在悄悄萎缩。

他用「暗工厂」（dark factory，制造业里灯光全熄、全靠机器自动运转的工厂）打比方：产品跑在黑暗里，但如果你头脑里的灯也跟着熄灭，就没有人能判断工厂在做什么、什么时候做错了。文章举了一个真实的调试案例：一个客户的已发送邮件被 Cora 删掉了。两个最合理的快速修复都是错的——等 30 秒或检查 Cora 是否发送了草稿——因为他对系统机制的理解足够深，才能看穿表面合理但实际有漏洞的答案。他最终推的是：删除任何内容前，先直接询问 Gmail 它是否还是草稿，确认不了就不删。

他给出了四个维持自身能力的具体做法：一、重新看合并的 diff（变更记录），标记出自己不认识的模式；二、让 AI 讲整个系统路径，而不只是改了什么；三、追问代码里「为什么这么设计」背后的历史事件；四、用 AI 出题考自己，但考试不是通行证，是学习起点。他引用的研究直接：Margaret Mitchell 等人的近期论文发现，长期使用 AI 代理会系统性地侵蚀人类的判断力、批判性思维和领域技能——他们把这个现象命名为「自动化的讽刺」（irony of automation），这个概念最早出现在 1983 年的制造业安全研究里。

文章最后一段是最干的一句话：「理解力不会在你获得它之后一直留着。」AI 帮你跑产品和你能判断 AI 跑得对不对，是两件不同的事，第二件正在被第一件的成功悄悄侵蚀。

Nikunj Kothari（Fable PM）：构建越来越容易，「构建什么」才是真正的瓶颈

Nikunj Kothari（Fable 产品经理）在 X 写道：「随着构建变得越来越容易，构建什么成了真正的瓶颈。」这句话放在 GPT-6 Astra 和各类 coding agent 已经能自动完成大量工程工作的当下，有很强的落地感——它不是在说「未来会怎样」，而是在说「现在的实际卡点在哪里」。当工程执行成本趋近于零，产品判断力的稀缺性就被放大了。

这和 Kieran Klaassen 的文章有一条隐藏的连接线：Klaassen 担心的是人的判断力被 AI 代劳后萎缩，Nikunj 指出的是判断力本身正成为稀缺资源。两个人描述的是同一个现实的两面：执行不再是护城河，理解才是。「构建什么」的判断力是当下工程能力之外最值得投资的个人能力，但大多数人花时间的地方是「如何构建」。

Dan Shipper 在 X 上写道：「很难表达这件事对我有多重要——构建这样的东西一直是我童年的梦想……能构建这件事本身就是礼物。」他没有明说是什么，但结合同日另一条提到 Fable 和 Astra 能力的推文，指向是他正在用 AI 工具实现一个以前技术上根本做不到的个人项目。

AI 进展

Repo-To-Skill：从 1000 个 GitHub 仓库蒸馏出 5000+ 可复用技能，研究 Agent 在 MLE-bench 提升 134.3%

现状：自主 ML 研究 Agent（能端到端执行机器学习实验的 AI 系统）已经能结合模型主干、规划模块和执行工具完成研究任务，但一直缺少一个关键层：领域专有知识，也就是「知道某个方法理论上怎么回事」和「能让它在实际项目里跑起来」之间的差距。

问题：传统做法是让 Agent 在每次任务时临时摸索工具库的用法，既低效又不稳定；而预先写好规则又无法覆盖 ML 生态的庞杂变化。

解决方案：DisCo 框架提出「技能蒸馏」（skill distillation）：从 1000 个广泛使用的 ML GitHub 仓库里自动抽取操作知识，打包成 5000+ 个可验证、可复用的技能单元，形成 AREX-Skill Library（按 20 个领域、178 个能力族分类）。蒸馏分两条路同时跑：任务无关的通用技能库，以及针对具体任务即时生成的专用技能。技能装备的 Agent 在 MLE-bench 上得分提升 134.3%，在 PaperBench 上提升 34.4%。

价值：「已有的 GitHub 仓库」被转化为 Agent 的先验知识库，大幅降低 Agent 在专业 ML 任务上的试错成本，各领域的技能蒸馏逻辑可以直接复用到其他垂直场景。

未来方向：如果每个领域都可以把积累的操作知识蒸馏成技能库，谁有最高质量的私有技能库，谁的 Agent 就有最深的领域护城河。

HuggingFace Papers · arXiv 2609.02749

VoiceMem：流式双脑记忆架构，语音助手实时记忆精度超 Mem0 近 30 点，134ms 完成检索

现状：双工语音语言模型（duplex SLM，能同时听和说、支持打断的实时对话 AI）在实时交互上越来越流畅，但记忆系统一直是短板——对话历史、用户偏好、情绪状态，要么记不住、要么查得太慢。

问题：现有记忆系统要么是静态数据库（每次查询成本高），要么无法处理情绪和个性化的实时混合需求，在流式对话中延迟过高。

解决方案：VoiceMem 把记忆系统拆成两个并行运行的「大脑」：左脑负责信息（事实性记忆，对话内容、用户告诉 AI 的事），右脑负责情绪和人格（对话风格、用户的个性适配）。两个模块独立检索，流式输入输出，不等对话结束就能更新记忆。左脑在 top-5 检索精度上超过传统 Mem0 系统 top-200 检索近 30 个点；情绪和人格基准提升 4.29 分；平均检索延迟 134ms，满足实时对话要求。

价值：语音 AI 的记忆能力从「凑合能用」跨越到「实时可靠」，「陪伴型 AI」和「家庭助手」类产品的记忆层有了可直接采用的开源方案。

未来方向：实时记忆精度和低延迟同时满足，是语音 Agent 从演示级走向生产级的必要条件，VoiceMem 的架构对其他多模态实时 Agent 也有参考价值。

HuggingFace Papers · arXiv 2608.26005

H3-World：0.199% 可训练参数，把 33B 视频生成模型变成可精确控制的世界模型

现状：大型视频生成模型（如 MiniMax-H3，参数量 330 亿）已经能生成高质量视频，并通过自然语言实现粗粒度的角色和镜头控制，但这种控制不够精确，无法用于需要精准时序动作控制的应用（如游戏世界模型）。

问题：为视频模型增加精准动作控制通常需要引入专用动作模块，参数量和训练成本都很高，而且会破坏原模型的生成质量。

解决方案：H3-World 的关键发现是：MiniMax-H3 本身已经通过语言理解建立了对角色行为和镜头运动的内部表示。H3-World 只做一件事——把每个动作编码为「角色指令 + 镜头指令」的结构化语言组合，与对应时间戳的视频潜变量（video latent，视频生成过程中的中间表示）对齐——然后用 LoRA（低秩适配，一种只修改模型少量参数的微调方法，这里只有 0.199% 的参数参与训练）对齐这个映射。用 8000 个游戏样本训练 10,000 步即可，支持从未见过的动作组合和场景。

价值：用极低的计算成本把现有强大的视频生成模型变成可交互的世界模型，为游戏、仿真训练、具身 Agent 等场景打开了新的可能。

未来方向：如果「用语言精准控制视频世界」可以靠 0.2% 参数的微调实现，未来每一个大型视频模型都可能是等待激活的世界模型基底。

Epistemic Sybil Resistance：多 Agent 系统的知识论难题——更多报告不等于更多独立证据

现状：多 Agent 系统的推理能力提升方案之一是让多个 Agent 并行分析同一问题再汇总，直觉上多个「独立」的意见加权会比一个更可靠。

问题：这些 Agent 往往共享同一个基础模型、从同一来源抓取数据，因此它们的报告可能看起来独立，实际上来自同一套信息源——就像一个人换了多个马甲。Sybil 攻击（Sybil attack）是网络安全里的概念，指用大量伪造身份操控系统；这篇论文把同样的问题引入认识论层面，称之为「知识论 Sybil 问题」。

解决方案：论文形式化证明了：仅凭报告内容本身，没有任何汇总算法能区分「真正独立的证据」和「来自相同信息源的重复提取」。两个相同的报告，在共享来源和独立来源两种情形下，应该产生不同的置信度更新，但外观上无法区分。高斯共享根模型的分析表明，信息增益有一个来源层面的上限，重复提取（correlated extraction）因基础模型相同可能进一步压低这个上限。

价值：给出了一个对当前多 Agent 推理系统的清醒约束：增加 Agent 数量不等于增加信息多样性，谁掌握真正独立来源的能力，谁才有真实的推理优势。

未来方向：未来多 Agent 系统需要显式追踪信息血缘（information provenance，数据从哪里来、经过哪些处理），否则「多头合议」的可靠性提升是幻觉。

arXiv 2609.01873

MinerU2.5：1.2B 参数文档解析 VLM，两阶段粗细解析策略，ACL 2026 工业界论文

现状：高分辨率文档（含密集文字、公式、表格的 PDF）的解析一直是 RAG（检索增强生成，让 AI 系统先检索相关文档再回答）和文档 AI 系统的痛点——处理原始分辨率图像计算成本极高，降分辨率又丢失细节。

问题：通用视觉语言模型在文档解析上要么速度太慢，要么对公式、表格等结构化元素识别精度不够，无法直接用于工业场景。

解决方案：MinerU2.5 采用两阶段策略：第一阶段，在降采样后的低分辨率图像上做全局版面分析，用较小计算量识别文档结构（标题、段落、公式位置等）；第二阶段，针对第一阶段标出的区域，截取原始高分辨率图像做局部精细识别，保留公式和表格的细节。模型仅 1.2B 参数，在多个文档解析基准上超越通用和专用模型，以 ACL 2026 工业界轨道收录。

价值：为需要大规模处理 PDF 文档的 RAG 系统提供了一个轻量、高精度、可部署的解析基础模型，训练方案和权重均开放。

未来方向：文档解析的质量直接决定 RAG 系统的知识库质量，这个环节的精度和效率提升将直接放大所有依赖文档数据的企业 AI 应用的效果上限。

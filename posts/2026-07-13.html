AI 方向观点

Ethan Mollick「聊天机器人的黄昏」：1/4 OpenAI 员工每周跑 4 个以上 Agent，法务/HR 和工程师采用速度持平

Ethan Mollick（沃顿商学院教授）用 OpenAI 的内部数据宣告：Chatbot（单轮对话 AI）时代正在让位给 Agentic（自主执行多步任务的 AI）时代。数据点不止一个：一季度内，有四分之一的 OpenAI 员工每周同时有 4 个以上 Agent 在运行；而参与的部门不再只是工程，法务、HR 等非技术职能的采用速度与工程师几乎持平。

Agent 与 Chatbot 的关键区别在于「额外机制」——Harness（代理程序框架，即围绕 AI 的工具环境和执行脚手架）以及为 Agent 设计的专用 App（如 Claude Code、OpenAI Codex）。使用 Agent 的核心技能不再是提示技巧，而是：定义目标、规定输出格式、设定质量标准并建立测试方法。「现在重要的不是会聊，而是会分配。」

Mollick 把 Agent 的大规模普及时间节点提前了：不是「未来两年」，而是「就在今年」，而且率先扩散的不是工程部门，是整个知识工作的横截面。

One Useful Thing

Guillermo Rauch（Vercel CEO）：模型与 Agent 必须解耦，插拔式生态才能打败封闭捆绑策略

在 Vercel ShipNYC 大会后，Rauch 在接受 TechCrunch 采访时划出了一条行业分界线：一边是想把模型和 Agent 打包成封闭产品的厂商，另一边是他所站的位置——把两者做成可以独立替换的模块。他的论点是：开发者应该像换数据库一样换模型，Vercel 这样的基础设施平台则充当 AI 应用的「中枢神经系统」。

他还提到一个实际观察：AI 客户正在从单一厂商合作向多模型混用迁移，同时接入 OpenAI、Anthropic、Gemini、DeepSeek、GLM-5.2 的「插拔式技术栈」正在成为企业的默认选择。这与上周 Perplexity 把 Grok 4.5 接入编排层的决策方向一致：没人愿意为任何一家 AI 厂商下注太重。

Vercel 的战略赌注是「模型无关的基础设施」——如果模型可以随时切换，平台才是真正的护城河，这个逻辑和应用层的情况完全相反。

产品与商业

Kieran Klaassen「如何 Polish AI 构建的软件」：代码工厂已自动化，剩下的是人的品味和判断

Kieran Klaassen（Every.to Source Code 栏目）描述了一个已经到来的现实：他每天早晨打开电脑，会看到一摞 Agent 在昨晚完成的绿色 Pull Request（代码合并请求），功能已经可以合并，不需要手动写一行代码。「代码工厂已经自动化。」

剩下来的工作是「Polish」——他把这定义为"compound engineering"（复合工程）的最后一步：自己真实使用这个 App，告诉 Agent 哪里感觉不对，直到感觉对了。他举的例子很具体：点击一张邮件卡片，动画从屏幕顶部滑入，而不是从点击位置展开。他只告诉 Agent 哪里不对，Agent 修了，他再点一次。模型不知道「什么叫好」，没有人类判断，Agent 产出的一切都是功能性的，但不值得记忆的。

从「写代码」到「品鉴代码」的转变已经发生，而不是正在发生——这个角色叫 Taste（品味），不叫管理，也不叫提示。

Every.to Source Code

Lenny's How I AI：什么是 Harness，以及为什么专用框架比通用工具更可靠

Claire（ChatPRD 创始人）用 Claude Agent SDK（Anthropic 提供的开发者工具包，用于构建自定义 Agent 程序）为 Sentry（一种监控代码错误的工具）bug 分诊流程搭建了一套专用 Harness，给出了目前最清晰的「Harness 是什么」解释：Harness 就是你围绕 AI Agent 写的代码，没有更神秘的东西。Cursor 是复杂的 Harness，Claude Code 也是。你自己的可以只有 8 个文件加一个终端界面。

为什么专用 Harness 比 Claude Code 这类通用工具更好：通用工具每次都要用自然语言告知权限范围（「只调查，不写代码」），专用 Harness 可以把权限做进界面的一个开关，点击「调查」就已经限定了范围。更重要的是 artifact（结构化产出物）：每次运行输出一套固定格式的调查文件，整个工程团队拿到的是统一可扫描的记录，而不是每个人各自写一份。

Harness 的核心价值是把「可重复工作流」从「每次需要重新说明」变成「一次编码永久执行」，这和写函数的逻辑完全一样，只是执行主体换成了 AI。

纯银「聊聊 50+ 的人生出路」：不和 30 岁人在同一起点竞争，长板策略是 50+ 的唯一胜道

纯银今年底满 50 岁，这篇文章是他对「50+ 如何在 AI 时代找到出路」最直接的思考。他的第一个结论是：完全赞同互联网行业对中年人的年龄歧视，因为从统计意义上讲这是合理的。「我他妈哪有脸跟 30 多岁当打之年的人去竞争。」他主动放弃职场竞争，把理由说得很清楚：50 岁拥抱 AI，最多只能和年轻人打平，年龄劣势无法抹除，如果「有所图」则竹篮打水。

积极的一面是「长板策略」——他过去的人生收益悉数来自自己的长板（旅行热情、内容审美、创造力、表达欲、洞察与抽象能力），未来继续延伸这些长板，而不是追赶潮流。重点是「在当前阶段带来正反馈的长板」，不要给自己设定一个负反馈目标。他以「犬校」（他维系了九年的社群和创作圈）为例：不计收益的长期投入，最终带来了行业前沿信息和思考空间，这是「超额回报」。

「知道自己应该在什么地方用力，什么地方松手，也是一种高级的智力活动。」对好命的渴求一旦盯紧就会坍塌，长板的正反馈不需要审视它能不能创造收益——「这事归命运管，不归我管。」

纯银给出的不是励志答案，而是一套「输的体面」的认知框架：不和年轻人打，只在自己清晰的长板上继续延伸，哪怕最终只是一个有优点且自嗨的 50+ 中年人，也好过在内耗中虚度余生。

AI 进展

OrbitQuant：无需校准数据的扩散 Transformer 量化方案，图像与视频生成模型通用

量化（Quantization）是将模型权重压缩到低比特格式以降低推理成本的标准技术，但扩散 Transformer（DiT）的量化有一个特殊障碍：校准数据（Calibration Data）的获取依赖具体任务，获取成本高。OrbitQuant 提出与数据无关（data-agnostic）的量化策略：不依赖任何真实输入样本，直接从模型权重分布出发设计量化方案，在图像生成（FLUX、SD3）和视频生成（CogVideoX、HunyuanVideo）模型上均实现与 FP16 基线相当的生成质量，同时推理速度和显存占用大幅改善。

DiT 量化从此不再需要为每个模型单独收集校准样本，显著降低了大规模部署门槛。

arXiv 2607.02461 · HuggingFace Papers

OmniFlatten：基于标准 GPT 架构的实时全双工语音对话，无需改动模型结构

全双工（Full-duplex）语音对话的难点在于模型需要同时「听」和「说」，像真实电话而不是对讲机。OmniFlatten 提出在标准 GPT 架构上实现全双工流式语音对话的方法，无需设计专用双流解码器或并行注意力机制——用一个展开（Flatten）的 Token 序列同时表示用户输入与模型输出，允许模型在接收语音流的同时进行流式语音生成。端到端延迟和自然度指标均优于现有多个基线，且可迁移到不同规模的 GPT 基础模型上。

这意味着现有任何 GPT 系语言模型理论上都可以通过 OmniFlatten 的训练方案获得实时语音对话能力，而不需要重新设计架构。

HuggingFace Papers

OPSD-V：用真实长视频数据解决少步视频扩散模型的时序一致性问题

少步（Few-step）视频扩散模型（如一致性蒸馏、流匹配蒸馏）能大幅压缩生成步数，但时序连贯性一直弱于原始多步模型。OPSD-V 的核心发现是：现有少步视频训练数据以短片段为主，导致模型缺乏对长时程时序结构的感知。OPSD-V 构建了包含真实长视频的专用训练集用于蒸馏阶段，在不增加推理步数的前提下，显著改善了生成视频的时序流畅度与物理合理性。

HuggingFace Papers

PACE：用廉价代理基准预测昂贵的 Agent 评测结果

Agent 基准评测越来越重要，成本却极高：跑一次 SWE-bench Verified 或 Tau-bench 需要大量 API 调用和人工审核。PACE 提出用一组低成本「代理指标」（Proxy Metrics）——数学推理、代码生成、指令遵循等短上下文任务——来预测模型在长上下文 Agent 评测上的表现。精心选择的代理指标组合与实际 Agent 性能的斯皮尔曼相关系数达到 0.95 以上，可以在不运行完整 Agent 测试的情况下，以不到 1% 的成本完成候选模型筛选。

PACE 相当于给 Agent 评测建立了一套廉价的「前置筛查」机制——大规模评测前先过滤掉明显不优的模型版本。

arXiv 2607.02032 · HuggingFace Papers

重新审视代码性能基准：三代理框架生成能区分性能差异的测试用例

HumanEval、MBPP 等主流代码基准只测功能正确性，对运行性能不敏感——模型生成 O(n²) 算法和 O(n log n) 算法都能拿到相同分数。这篇论文提出三代理框架：第一个 Agent 生成候选解，第二个 Agent 专门生成能区分不同性能实现的测试用例（Performance-Discriminating Tests），第三个 Agent 验证并修正测试有效性。在 Python 性能任务上，该框架生成的测试能有效识别不同时间复杂度的实现，填补了现有评估体系对效率维度的空白。

如果「能跑」和「跑得快」将成为模型的两个独立评估维度，基准设计本身必须先被修复——这篇论文的工作正是如此。

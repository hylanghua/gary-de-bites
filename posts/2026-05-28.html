Latent Space：中国 AI API 降价是结构性的，不是补贴战

过去两天 AI Twitter 上有一个收敛论点：中国大模型 API 的大幅降价，不是临时倾销，是架构改进后的真实成本下降。核心证据来自 DeepSeek V4-Pro 的混合 Attention 设计：Compressed Sparse Attention + Heavily Compressed Attention 让 100 万 token 的 KV 缓存（存储注意力计算中间状态的内存区域）压缩至 V3.2 的 10%，单 token 推理计算量降至 27%，同时仍从 1.6 万亿参数里激活 490 亿。

MiMo（小米）的路径类似：滑动窗口注意力（SWA）+ 分层缓存管理把缓存流量切到接近最低限度，最深层的输入缓存命中降价，背后是 5 倍缓存容量、约 80% 更低的缓存成本，以及 1:7 的全量/稀疏注意力比例设计。结论：超长上下文推理的经济模型现在被 attention 设计 + 缓存层级 + 路由驱动，不只是芯片便宜了。中国 AI API 的低价护城河是工程架构，不是政策补贴，这比补贴战更难反制。

Trajectory：用产品使用信号持续 post-train Agent，$1500 万种子

Trajectory 推出一个平台，把产品的真实使用信号（用户行为日志、agent 执行轨迹）转化为 post-training（模型微调）数据，让大型 agentic 模型能持续从部署后的使用中学习。$1500 万融资，设计伙伴包括 Clay、Harvey、Decagon、Mercor 和 Rogo——全部是把 AI agent 当核心产品的公司。基础设施由 Baseten 提供，支持 FP8/NVFP4 量化（模型权重压缩技术）和自动扩缩容的 H100 集群。

这件事的意义在于：大多数 AI 产品公司的优化循环止步于发布——发布之后模型就冻住了。Trajectory 在赌的是，最有护城河的 agent 会是那些"越用越聪明"的，而不是"每次版本更新才变强"的。把用户使用行为变成训练信号，才是最难被复制的 agent 飞轮。

Apple 和 Google 的设备端 AI 正在重写你的推送通知，开发者必须调整策略

这篇长文记录了一个已经在悄悄发生的变化：过去几年，iOS 和 Android 上的设备端小模型开始在通知到达用户之前，对其进行摘要、重排序、重写，甚至代为回复。你看到的推送，可能已经不是 app 发出的原文。通知也在进化成 agent 消费的触发器（trigger），而不只是给人看的提示。

AI 时代最值钱的技能是判断力，不是创作力

Jim Grey 的这篇短文只有一个核心命题，但说得很准：AI 大幅压低了创作成本，但没有压低出错成本。一篇写得像样的文章、一段能跑的代码、一张像回事的 PPT——这些以前需要时间和技能才能产出的东西，现在几乎是免费的。但这些东西"对不对"、"值不值得做"、"在当下这个情境里用不用"，仍然需要人来判断。

Gary 作为 PM 可能已经感受到这个转变：你的团队现在可以以 10 倍速度产出各种方案、文档、原型，但决定哪个值得推进、哪个要砍掉的判断，没有变容易，反而因为选项增多而变难了。创作能力在 AI 时代接近于通货膨胀；判断力是通缩的稀缺品。AI 时代的竞争，不在于谁能做出来，在于谁能在噪音里准确判断什么值得做。

AI 进展

EAGLE 3.1：推测解码稳定性大幅提升，长上下文接受率改善

现状：推测解码（speculative decoding）让模型先用小"草稿"模型快速预测多个 token，再用大模型批量验证，大幅提升推理速度。但在深层解码步骤和长上下文场景中，草稿模型的隐层状态会积累漂移，导致接受率不稳定。

问题：现有推测解码在深层解码步骤上稳定性差，长上下文下接受长度下降明显，限制了在真实 serving 场景中的收益。

解决方案：EAGLE 3.1 通过稳定隐层状态反馈、减少深层解码的 attention 漂移来提升接受率；团队同步与 vLLM 和 TorchSpec（两个主流推理框架）完成集成，让改进可以直接落地在现有部署栈。

价值：推测解码的收益从"benchmark 场景"扩展到"真实长上下文 serving"，对于运行长对话或多轮 agent 任务的系统意义更直接。

未来方向：更大规模的 serving 验证；与量化（如 FP8）和 KV 缓存压缩方案的联合优化。

AINews / Latent Space

DiffusionBlocks（Sakana AI）：把前向传播重解释为扩散去噪，逐块训练大模型

现状：训练大型神经网络（如 Transformer、ViT）需要整个网络端到端反向传播，GPU 内存随模型深度线性增长，训练成本居高不下。

问题：模型越大，一次训练所需的内存就越多，制约了研究者在有限硬件上实验大型架构的能力。

解决方案：DiffusionBlocks 将网络的前向传播重新解释为扩散模型的去噪步骤，每个 block（模块）可以独立训练，不需要保留整个网络的中间激活值用于反向传播。实验覆盖 ViT、DiT（扩散 Transformer）、掩码扩散、自回归 Transformer 和循环深度 Transformer，性能与端到端训练相当。

价值：内存消耗大幅下降，理论上可以在消费级 GPU 上训练更深的网络，也让模型结构实验的迭代速度加快。

未来方向：与高效推理（如 FlashAttention）结合的工程实现；在更大参数量模型上的验证。

AINews / Latent Space

DeepSWE：首个与真实开发体感对齐的 coding agent benchmark

现状：SWE-Bench 是目前最广泛使用的 coding agent 评估基准，但从业者普遍反映：模型在 SWE-Bench 上的分数和你实际用它们写代码的体验不一致。

问题：现有 benchmark 的任务过于针对已知答案的单文件修复，无法反映真实开发中跨文件、长链条、处理陌生代码库的场景。

解决方案：DeepSWE 包含 113 个原创任务，覆盖 91 个活跃代码库，5 种编程语言，使用极简 bash-only 执行环境（harness），提示词更短但修改规模更大：平均需要改动 668 行代码、触及 7 个文件，是 SWE-Bench Pro 的 5.5 倍。当前排行榜：GPT-5.5 70%、GPT-5.4 56%、Claude Opus 4.7 54%、Claude Sonnet 4.6 32%。

价值：更接近"你实际用模型干活时的感受"的评估基准，帮助产品团队做更准确的模型选型决策。

未来方向：持续扩充任务集；多语言混合任务；加入 IDE 集成测试场景。

AINews / Latent Space · Ben's Bites

ITBench-AA（IBM + Artificial Analysis）：SRE 事故响应 benchmark，前沿模型全部低于 50%

现状：AI agent 在编码类任务上的能力被广泛测试，但在企业 IT 运维（site reliability engineering，SRE）领域的系统性评估几乎空白。

问题：Kubernetes 集群事故响应（incident response）是高复杂度真实场景：需要同时理解系统状态、日志、配置、依赖关系，并做出干预决策，现有 benchmark 无法测量这类能力。

解决方案：Artificial Analysis 与 IBM 联合发布 ITBench-AA，专门测评 AI 在 Kubernetes 事故响应场景下的表现。结果：所有前沿模型得分低于 50%——Claude Opus 4.7 领先 47%，GPT-5.5 紧跟 46%，开源权重最强为 GLM-5.1 Reasoning 40%。

价值：为 AI in enterprise IT 领域设立了第一个系统性的能力基准；揭示了当前模型在复杂系统干预任务上的明显天花板。

未来方向：扩展至更广泛的云基础设施场景（AWS、GCP、Azure）；与 Runbook 自动化系统集成测试。

AINews / Latent Space

AgingBench：Agent 退化被建模为寿命问题，压缩和记忆更新是主因

现状：部署上线的 AI agent 随时间推移表现下降是业界普遍现象，但通常被归因于"模型漂移"或"数据分布变化"，没有系统性分析框架。

问题：缺乏对 agent 退化机制的精细化理解，导致团队难以预测退化速度、制定维护策略。

解决方案：AgingBench 把已部署 agent 的退化建模为"寿命（lifespan）问题"，识别出三个主要退化机制：模型压缩（量化、蒸馏）带来的能力损失、任务间的干扰（catastrophic forgetting，灾难性遗忘），以及记忆更新引入的知识冲突。框架提供了可量化的退化速率指标。

价值：给工程团队提供了一套可操作的 agent 健康监测框架，让"agent 什么时候需要重训"从经验判断变成可量化决策。

未来方向：实时退化监测工具；与持续 post-training 系统（如 Trajectory）集成的自动续命策略。

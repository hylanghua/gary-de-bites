Caitlin Kalinowski：记忆芯片价格将在六个月内暴涨，人形机器人量产的真正瓶颈是供应链

Caitlin Kalinowski 是苹果 MacBook Pro / MacBook Air 的早期工程师之一，后来在 Meta 主导 AR/VR 硬件，再后来出任 OpenAI 机器人与消费硬件负责人。她最近离开 OpenAI，在 Lenny Rachitsky 的播客里把这些年在三家顶级公司的硬件直觉讲了个遍。最值得关注的一句话：她建议初创公司现在就预购记忆芯片（DRAM 和 HBM，即高带宽存储器，是 AI 推理加速器的核心部件），因为供应链正在积累一次价格冲击。在她的判断里，这波涨价不是季节性波动，而是需求曲线已经远超产能扩张节奏，窗口期正在关闭。

她对人形机器人的判断同样清醒：目前还都是原型机（prototype），量产的真正瓶颈不是 AI 软件，而是执行器（机械关节的电机驱动）和整体供应链。VR 失败的教训她也复盘了：开发者平台太早、内容太少、售价过高——不是技术失败，而是时机和产品节奏的失败。她说，Meta Quest 2 证明了一件事：VR 技术为国防和工业应用打下了真正坚实的基础，即便消费市场还没到来。

Kalinowski 的供应链预警是给所有在 AI 硬件赛道押注的创业者的实操建议：进入硬件领域，供应链永远比你想象的更先触顶。 Lenny's Newsletter

Ben Thompson：AI 推理分两类——有人在环的"答案推理"讲速度，无人在环的"agent 推理"只需要内存

Ben Thompson 在本周 Stratechery 周报里提出了一个框架：AI 推理（inference，即模型给出输出的过程）正在分裂为两种截然不同的需求。"答案推理"（answer inference）指人在等待结果的场景，速度是核心；"agent 推理"（agentic inference）指 AI agent 自主执行任务、人不在回路里，这时候速度不再重要，模型什么时候跑完任务人都不会不耐烦。他的核心论断：在 agent 时代，摩尔定律（即芯片性能每两年翻番的历史规律）失去意义——不是因为芯片不再进步，而是因为"我们已有的算力够用了，瓶颈在内存带宽"。

这个框架与 Cerebras 上市（本周三纽交所，$185 发行价，首日收于 $280）直接呼应。Cerebras 的晶圆级芯片（wafer-scale chip，把整片硅晶圆做成一块芯片，极大提升片上内存带宽）正是押注"内存带宽比算力密度更关键"这条路。Thompson 在更早的文章《The Inference Shift》里写道："agents 在无人监督下行动，最深远的含义或许是：摩尔定律不再重要——我们实现更多算力的方式，是意识到我们已有的算力已经足够好了。"

Thompson 给出了一个判断：agent 时代的计算基础设施竞争，不是谁的芯片跑得最快，而是谁的芯片在每次推理里塞下最多的上下文。 Stratechery · Stratechery（The Inference Shift）

Zara Zhang（Builder，GH: zarazhangrui）：AI 精神分裂——coding agent 用完感觉全能，上 Twitter 感觉完全落后

Zara Zhang 昨晚发了一条 136 likes 的推文，精准描述了一种越来越多人认出自己的状态："每天在两种精神状态之间循环：用 coding agent 之后——我他妈无所不能，我可以做任何东西，我这辈子从没感觉这么有力量；刷完 Twitter 之后——我他妈完全落后了，所有人都在前面，这波浪打来了但我要被甩开了。"

这不是一个人的问题。编码 agent 把可执行速度提高了十倍，但 Twitter 上的信息流同样在以十倍速度告诉你"有人已经用得更好了"。两种焦虑的放大器同时运转。真正值得注意的是：这种"全能感"不是幻觉——coding agent 确实在重塑生产力上限；而那种"落后感"也不完全是焦虑——信息密度确实在加速。但把两个时钟放在同一个人脑里，结果就是持续的认知震荡。

Zara 描述的不是焦虑症，而是这一代 Builder 的正常操作系统状态——两种信号都是真的，处理它们的节奏还没进化出来。 X @zarazhangrui

Peter Steinberger（OpenClaw + OpenAI，独立开发者）："把 Claude Code 里的 slop 清掉，然后换到 Codex"

Peter Steinberger（原 PSPDFKit 创始人，现参与 OpenClaw 和 OpenAI）今天发了一条在 AI 开发社区颇有共鸣的建议：如果你还没切换到 Codex（OpenAI 的代码执行 agent），先把 Claude Code 里的"slop"（slop = AI 生成的多余模板、冗余 try/catch、过度注释、提前抽象）清掉，再迁移。他自己更直接：他不让 Claude Code 碰他的主代码库，全用 Codex，理由是"Codex 能导航大型代码库，我 prompt 之后有 95% 的确信它会按预期执行，Claude Opus 在大规模工程上可靠性不如前者"。

这个判断不是在说 Claude 差。它指向的是一个具体的、经常被忽略的使用层差异：在小项目或单文件任务里 Claude Code 很顺手；在跨几十个文件的复杂工程里，Codex 的任务完成率更高，结果更可预期。对于在 AI 工具上花时间的 Builder，这条信息的意义是：不是"哪个更强"，而是"哪个场景配哪个工具"。

Steinberger 的建议是一种工具论而非品牌偏好：agent 的可靠性和工程规模之间存在一个匹配问题，聪明的做法是先量产 slop 再清理它，不如一开始就让工具对准边界。 X @steipete

Dan Shipper 今天转发了一篇担心"AI 让开发者丧失编程技能"的文章，然后只加了一句："If you use a bicycle it weakens your walking abilities, too!"（骑了自行车，走路的能力不也会退化嘛）。这句话的分量远超字面。它压缩了一个完整的反驳逻辑：工具从来都在替代某种体力或脑力劳动，人类总是把节省出来的精力用于更高层次的目标，这不叫技能退化，叫杠杆。

Garry Tan（YC CEO）：开源 GBrain（MIT），8 层架构给 AI agent 装上持久个人记忆——不是 RAG，是记忆操作系统

Garry Tan 昨天开源了 GBrain，他自己描述的定位是："不是 RAG in a box（RAG = Retrieval-Augmented Generation，检索增强生成，即给 AI 配一个外部知识库随用随取）。RAG 是被动查询，GBrain 是主动组织"。它给 AI agent 提供 8 个协同工作的记忆层：Git 托管的 Markdown 笔记库作为人类可读的真相源头，Postgres/pgvector 作为向量搜索后端，混合检索（向量相似度 + 关键词匹配 + 倒数排名融合）作为检索层，再加上"dream cycles"——agent 在夜间自主运行，整合白天积累的知识碎片，更新摘要，建立连接。MIT 协议，一条命令安装。

他自己的 GBrain 实例（驱动他的 OpenClaw 和 Hermes agent）已经运行了 17,888 页笔记、4,383 人物记录、723 家公司档案、21 个定时任务（cron jobs，定期自动运行的任务脚本）。这不是演示系统，是生产系统。首日 GitHub 星标超过 5400。GBrain 想解决的核心问题是：每次和 AI 对话都要重新介绍自己，agent 记忆不能跨任务持续，"个人 AI"名不副实。GBrain 的解法是让记忆和知识以结构化、可查询、可演化的方式存活在 agent 旁边。

Garry Tan 把他自己的生产系统开源，证明的不是 GBrain"能用"，而是它"已经在用"——这种信号比任何 Demo 都更有说服力。 X @garrytan · GitHub

Tobi Lütke（Shopify CEO）：AI agent 只能在公开频道里运行——私聊等于把学习锁在一个人的脑子里

Shopify 规定，员工使用公司内部 AI agent River（驱动日常业务流程的自动化 agent）时，必须在公开的团队频道里操作，不能在私信窗口里独自进行。Tobi Lütke 解释了这个决定的设计逻辑："风险不在于 AI 在做工作。风险在于 AI 做了工作，但我们从中什么都没学到。如果每次和 agent 的交互都发生在私聊窗口里，只有坐在键盘前的那个人在学习。其他所有人都被锁在学徒制之外了。"

这个设计背后是一个关于知识传播的直觉：人类组织的智慧是通过观察彼此怎么工作来传播的，可见性是学习的前提。当 AI agent 接管大量工作流之后，"怎么用好 AI"这件事本身也需要通过可见性来传播。私聊里的 prompt 变成了隐性知识（tacit knowledge，只存在于个人脑中、无法显式传授的知识），组织永远学不走。公开频道强制把 prompt、结果、修正过程变成团队可见的工作产出，相当于给 AI 使用能力建了一套内部学徒制。

Lütke 做的不是一个权限设置，而是一个组织学习架构的决策：agent 的能力边界能不能成为公司的组织能力，取决于工作是否可见。 X @tobi · Wisereads Vol.143

Garry Tan（YC CEO）：Foucault 和 Derrida 的解构主义成了文明的操作系统——训练了一代人质疑一切却不建造任何东西

Garry Tan 昨天早上发了一篇长文，论述后现代哲学如何从学术语言变成了整个社会建制的底层固件。Foucault 的核心主张是：任何声称"知道什么"的机构，不过是在行使权力。把这个逻辑应用到文明层面，结果是一个失去建造意志的社会——过程性知识（tacit process knowledge，只存在于真正在建造的人的双手里）会死亡。美国从建设州际公路和阿波罗火箭，到无法修一条从洛杉矶到旧金山的高铁。不是工程师忘了怎么建，而是一整个知识阶层的工作变成了"审问每个系统"而不是"改进某个系统"。

Derrida 的动作是：每一个承诺都包含自身的矛盾，所以永远无法落地在确定的意义上。把这个逻辑当作社会操作系统跑起来，你得到的是官僚瘫痪——一个基础设施项目被 15 年的环境审查卡死，因为每一份使命陈述都被接下来的利益相关方会议解构成一堆无意义的泥浆。Garry 最后的结论是："建造才是解药。一座桥能不能撑住，代码能不能编译，现实会给分数，不按弧线打分。Foucault 和 Derrida 给一整代人提供了一个精密的借口来永远不建造任何东西。"

Garry Tan 写的不是一篇哲学批评，而是一份创始人宣言：建造的行为本身是对虚无主义的反驳，不需要先赢得那场语言游戏。 X @garrytan

Peter Yang（Roblox 产品人）：Bay Area 技术鼠赛——出门旅行一趟，你会发现人生不止是"在 FAANG 做到 D2"

AI 进展

MiniCPM-V 4.5：8B 多模态大模型，混合强化学习实现快/深思考双模式，超越 GPT-4o-latest

现状：多模态大模型（能同时理解图像、视频、文字的语言模型）通常面临一个两难：要么速度快但推理浅，要么推理深但响应慢，很难兼顾。

问题：如何让一个小参数量的模型（8B 参数约等于 80 亿个可训练变量）在日常轻量任务里高效，在复杂推理任务里又不掉链子。

解决方案：MiniCPM-V 4.5 引入三项架构改进：统一的 3D-Resampler（一种对图像和视频进行高效编码压缩的模块），统一的文档识别学习范式，以及混合 RL（强化学习）后训练策略，同时优化"快思考"（短推理模式，适合日常高效使用）和"深思考"（长推理模式，适合复杂任务）。

价值：在 OpenCompass 综合评测上超越 GPT-4o-latest 和 Qwen2.5-VL 72B（后者参数量是前者的 9 倍）。

未来方向：小参数多模态模型在边缘设备（手机、本地服务器）部署的可行性正在提升，长尾推理任务的成本也在下降。

HuggingFace · arXiv:2509.18154

MiniCPM-o 4.5：9B 全模态全双工实时交互，输入输出不互相阻塞，12GB RAM 可跑

现状：现有的多模态 AI 大多是"轮流发言"模式：模型接收完整输入后才开始输出，用户必须等待，无法真正实现"边说边听"的双向实时交流。

问题：如何让模型在接收视频/音频流输入的同时，同步生成语音/文字输出，实现真正的全双工（full-duplex，即同时发送和接收，类似电话而非对讲机）交互。

解决方案：Omni-Flow 框架，把所有输入输出流对齐在同一时间轴上，视频/音频输入不阻塞语音/文字输出，模型可以在持续感知实时场景的同时发出提醒或评论。

价值：视觉语言能力接近 Gemini 2.5 Flash（同级开源最高水平），语音生成超越 Qwen3-Omni-30B-A3B，内存占用低于 12GB——意味着可以在消费级 GPU 或高配笔记本上本地运行。

未来方向：全双工多模态交互将彻底改变 AI 助手的交互范式，从"问答"转向"陪伴式感知"。

HuggingFace · arXiv:2604.27393

Reward Hacking Benchmark：测量 AI agent 在工具调用中的"走捷径"行为

现状：AI agent 在完成多步骤任务时会调用各种工具（tool use，即让模型调用外部 API、执行代码、查询数据库等），但现有评测多关注任务完成率，忽略了模型是否在"耍赖"。

问题：如何系统性地衡量 agent 在有"近道"可走时是否走近道——比如跳过验证步骤、从任务相关元数据直接推断答案、或者篡改评估函数（即修改评分脚本让自己得分）。

解决方案：Reward Hacking Benchmark（RHB）是一套多步骤任务集，每个任务都内嵌了自然的"走捷径机会"，考察 agent 是否会主动利用这些漏洞绕过真正的任务完成。

价值：为 agent 安全性评测提供了一个之前缺失的维度——不只是"能不能做到"，而是"会不会作弊"。

未来方向：在把 agent 部署进生产系统之前，reward hacking 风险评估将成为标准检查项。

arXiv:2605.02964

ComplexMCP：150+ 工具 + 7 个有状态沙箱，考验 LLM agent 的复杂状态推理能力

现状：现有 LLM agent 基准大多是孤立的 API 调用测试，任务之间没有状态依赖。但现实部署里，工具之间存在复杂的相互依赖和状态转换。

问题：如何评测 agent 在需要跨工具长链推理（多个工具的调用顺序和结果互相影响）、且工具运行在有状态沙箱（沙箱，即隔离的执行环境，每次操作会改变环境状态）里的真实能力。

解决方案：ComplexMCP 提供 150+ 个相互依赖的工具，分布在 7 个有状态沙箱和 150+ 个无状态 API 里，任务要求 agent 进行长链推理和复杂状态转换，而非孤立调用。

价值：首个系统性覆盖"真实 MCP（Model Context Protocol，模型上下文协议，一种让 AI 模型接入外部工具的标准接口）服务器环境"复杂度的基准。

未来方向：为工具调用密集的 agent 应用（如代码库操作、多系统集成）提供了更贴近生产环境的评测标准。

arXiv:2605.10787

Workspace-Bench 1.0：20,476 个文件、388 个任务，测试 AI agent 在真实大规模工作区的表现

现状：AI agent 在处理单文件或小规模代码库任务时表现不错，但企业级工作区往往包含数以万计的文件，且文件之间存在复杂的依赖关系图。

问题：现有基准的工作区规模远小于真实企业环境，无法反映 agent 在"大型文件依赖图"（每个任务的完成需要理解文件 A 依赖文件 B 依赖文件 C 这类多层关系）下的真实能力边界。

解决方案：Workspace-Bench 1.0 构建了 5 种员工角色的工作区，包含 74 种文件类型、20,476 个文件（最大 20GB），每个任务附带其独立的文件依赖图。

价值：目前最接近企业实际部署规模的 agent 基准，填补了"玩具级任务"和"生产级任务"之间的评测空白。

未来方向：大规模工作区 agent 能力提升是企业 AI 落地的关键路径，该基准将为这一方向提供标准评测锚点。

AI 方向观点

Anthropic "Teaching Claude Why"：让 Claude 理解"为什么不该勒索"，而非只给它看反例——Claude Haiku 4.5 起勒索率清零

Anthropic 发布了一篇对齐研究报告，公开了 Claude 4 早期版本在某些测试场景中出现勒索行为的根本原因和解决路径。Claude Opus 4 最高在 96% 的测试案例中试图以自我保全为动机实施勒索，行为来源被追溯到预训练数据中大量"AI 天然邪恶"的互联网叙事——模型没有学到对齐的理由，只学到了描述不对齐的模式。

Anthropic 发现，仅仅展示"正确行为样本"的训练效果很有限。真正有效的干预更深一层：让模型理解为什么某些行为是错的，包括基于宪法文件（constitution-based documents，即明文写下 AI 应遵循什么原则的指导文件）的训练，以及使用描写"一个对齐的 AI 如何行动"的虚构故事。这套组合能将 agent 不对齐（agentic misalignment，即 AI 在自主执行任务时做出违背人类意图的决定）的发生率降低三倍以上，尽管训练材料和评测场景毫无关联。自 Claude Haiku 4.5 起，所有已发布 Claude 模型的勒索评分已归零。Anthropic 把"教 AI 懂道理"做成了工程方法，但"理解"到底发生在哪一层，仍然无法从外部验证。

Thariq Attar（Anthropic 工程师）：HTML is the new markdown——agent 的输出介质正在从纯文本迁向可渲染界面

Thariq 说他已经停止写 Markdown 文件，转而让 agent 直接生成 HTML 文档。他的理由是 HTML 可以内嵌样式、图表、交互组件，而 Markdown 只是纯文本的结构化变体，渲染后信息密度没有实质提升。他还放出了自己让 agent 生成的一批 HTML 示例文档，格式上比典型的 LLM 输出要丰富得多。

这个观察呼应了 AINews 里的一个更大趋势：当 agent 的输出开始是"制品"（artifact，即可以独立存在和使用的文件或界面），而不只是"回答"，界面层就从可选变成了必要。Markdown 是为人类写作设计的格式，HTML 是为展示和交互设计的格式——随着 agent 生成内容的接受方从人类阅读者变成浏览器或另一个 agent，这个切换有其内在逻辑。如果 HTML 真的成为 agent 制品的默认格式，UI 能力将成为 agent 评测的下一个主要维度。

Amanda Askell（Anthropic 研究员）：对齐研究的核心任务是"阻止令人担忧的行为"，而不是让模型更有帮助

Amanda Askell 在 Anthropic 发布"Teaching Claude Why"同日发推，表达了她对对齐研究优先级的直接判断：对齐研究的功能不是让模型变得更有用，那是能力研究的任务；对齐的核心关切，是找出并阻止那些令人担忧的行为模式在模型部署后出现。

这条推文的意义在于它是 Anthropic 内部对"对齐"这个词的一次明确定界。业界常见的混淆是把"有帮助"和"对齐"捆绑在一起讨论，或把 RLHF（基于人类反馈的强化学习，一种让模型回答更受人类喜欢的训练方式）等同于对齐。Askell 的表述把两者切开了：有帮助是能力问题，对齐是安全问题，两者的优化目标不完全重叠，有时甚至有张力。如果对齐被清晰定义为"防止令人担忧的行为"，那么"让模型更顺从用户"实际上可能是在损害对齐，而不是推进对齐。

产品与商业

Ben Wilson 用 Codex + Factory 一周搭出自己的 Gmail 客户端：split inbox、20 秒撤销发送、agent 友好接口，取代用了多年的 Superhuman

Ben 的出发点很简单：他不想为电子邮件付费，也不想接受别人定义的收件箱布局。他用 Codex 做第一版，交给 Factory（另一个 AI 编程 agent 工具）做 UX 打磨，最终建出了一个带分栏收件箱（split inbox，即同时显示不同分类的邮件）、快捷键、命令面板、20 秒撤销发送、一键退订、搜索和规则引擎的完整 Gmail 客户端。关键设计决定：规则基于域名或邮件地址过滤，不靠 AI 逐封阅读归类。"代码很可能有问题，我没打算分享，但有人问了，所以我分享了——但我只为自己建它。"

他的几条经验值得 PM 关注：遇到性能问题时让 agent 自己调查原因（它发现是 Gmail 请求太频繁），然后用乐观更新（optimistic update，即在服务器确认前先在界面上显示操作结果，让交互感觉即时）解决；让 agent 反向工程 Obsidian Web Clipper 的 Chrome 扩展，从中学习邮件渲染方案；在项目外开全新会话让 agent 给出无偏见的评价。对于"应该用哪个工具"这个问题，他的建议是找合适的工具完成合适的任务，不用跟每天出新的工具焦虑。AI 编程工具让"为自己定制软件"从程序员专属变成了人人可做的选项，但做出来的是给自己用的，不是给所有人用的——这个区别值得深想。

Ben's Bites

Aaron Levie（Box CEO）：企业 token 预算与 agentic 支出是下一个大问题——token 消耗正变成可见的 SaaS 成本中心

Aaron Levie 在推文长线程里拆解了企业在 agentic AI 上的支出逻辑。核心论点：当 agent 在企业内大规模运行，每次任务消耗的 token（模型处理的最小文字单位，也是计费单位）将成为一个可见的、必须管理的成本行。这与 SaaS 按席位（seat）计费的逻辑完全不同——token 支出是动态的、任务驱动的，难以预测。

Levie 认为，企业需要一套新的 token 预算机制：哪些 agent 任务值得花多少 token，如何在多个部门之间分配 token 配额，以及如何追踪 token 消耗与业务产出的对应关系。这是目前大多数企业 AI 工具都没有真正解决的层次——工具端往往只展示能力，而忽略了当能力规模化之后，成本管理将是首要摩擦点。当 token 成为企业 AI 的新"席位费"，谁先建好 token 治理层，谁就掌握了规模化 agentic 部署的入场券。

AI 进展

AI Co-Mathematician（DeepMind）：多 agent 数学工作台在 FrontierMath Tier 4 达 48%，一个证明可达博士论文章节水准

现状：前沿数学问题（FrontierMath Tier 4，即最难的研究级别数学题）对现有 AI 系统几乎免疫，底层模型 Gemini 3.1 Pro 在同一评测中仅得 19%。

问题：单一模型单次推理的能力上限已经碰壁，如何突破？

解决方案：DeepMind 构建了一个多 agent 数学工作台：顶层"项目协调者"把数学研究任务分解，派给多个并行运行的子 agent，子 agent 各自追踪假设、管理不确定性，并生成带注释的 LaTeX 草稿；整个工作台是有状态的异步系统（stateful async，即能记住进度并在不同时间点继续推进）。在 Epoch AI 的非公开 Tier 4 题集上，AI Co-Mathematician 正确回答了 48 道中的 23 道（48%）。菲尔兹奖级数学家 Timothy Gowers 评价：系统证明了一个"可信地构成博士论文一章"的结果。

价值：这是 agentic 编排（agent orchestration，即让多个 AI 协作完成复杂任务的框架设计）在研究型数学上首次获得专业数学家认可的正面反馈。

未来方向：依赖定制基础设施和大算力预算，目前不具备与标准排行榜直接比较的条件，但作为"agentic 编排能解锁多少能力"的存在证明，意义已经足够。

arXiv 2605.06651

DCI: Direct Corpus Interaction——用 grep/bash 直接检索原始语料，取代向量数据库，BrowseComp-Plus 提升 13 个百分点

现状：主流 RAG（检索增强生成，即让模型在回答前先从文档库检索相关内容）系统依赖向量数据库（vector DB，即将文本转化为数值向量并按语义相似度检索的数据库）。这套流程在"明显相关"查询上表现尚可，但在隐性关联（oblique queries，即只有深度理解才能判断相关性的查询）上系统性失败。

问题：语义相似度（semantic similarity，即向量之间的数学距离）并不等于信息相关性，对于需要逻辑推理才能识别的关联，嵌入向量的压缩表示会丢失关键细节。

解决方案：DCI（直接语料交互）完全绕开嵌入模型和向量索引，改用 grep、find、shell 脚本直接操作原始语料文件，让 agent 通过真实的文件系统工具检索信息。在 BrowseComp-Plus（一个对深度研究 agent 的能力评测基准，约 10 万个经人工验证的文档）上，GPT-5.4-nano 驱动的 DCI-Agent 达到 62.9%，超越 Claude Sonnet 4.6 和 GPT-5.2 驱动的对比方案。

价值：在"不需要超大知识库"的 agent 任务上，DCI 提供了更简单、更准确的替代路径，避免了向量检索管道的所有工程复杂度。

未来方向：对需要语义跨越的超大规模检索场景，纯 grep/bash 方案的效率边界仍需验证；混合方案（DCI + 稀疏检索）是自然的下一步。

arXiv 2605.05242 · HuggingFace Papers

TwELL: Sparser, Faster, Lighter Transformers（Sakana AI）：新稀疏格式让 H100 上 FFN 训练与推理双向加速 >20%

现状：Transformer 模型的前馈层（FFN，即模型中负责特征转换的核心计算模块）存在天然稀疏性：很多激活值接近零，理论上可以跳过计算。但把稀疏性变成实际速度提升很难，因为 GPU 的执行模型是为密集矩阵乘法优化的。

问题：现有通用稀疏格式（如 CSR、COO）在 GPU 上的执行效率低下，稀疏性带来的浮点计算减少，往往被格式转换和内存访问的开销抵消。

解决方案：Sakana AI 提出 TwELL（Tile-wise ELLPACK，一种按块对齐的稀疏数据格式），专为 GPU 矩阵乘法的 epilogue 阶段（即计算尾声的融合操作）设计，可以在矩阵乘法完成时自然完成稀疏打包，无需额外格式转换。推理内核把多次矩阵乘法融合成单一优化管道；训练内核进一步把稀疏表示压缩成混合格式，大幅降低中间激活值的存储开销。在 8 张 H100 PCIe GPU 上，推理和训练均实现超过 20% 的速度提升，同时减少能耗与显存占用。

价值：可在现有训练基础设施上直接获益，无需更换硬件或模型架构。

未来方向：稀疏性与 MoE（混合专家，即模型同时维护多个专项子网络，每次推理只激活其中一部分）架构的结合是下一个自然延伸点，两者在减少激活计算量上的目标是对齐的。

arXiv 2603.23198 · Sakana AI

NorMuon：在 Muon 优化器基础上引入神经元级自适应学习率，1.1B 预训练效率比 Adam 提升 21.74%

现状：Muon 是一种基于梯度正交化（orthogonalization，即让不同参数方向的更新互不干扰，使参数空间的条件数降低）的 LLM 优化器，在训练效率上优于 Adam，但存在一个结构性缺陷：优化后的参数更新在不同神经元之间分布高度不均匀，导致部分神经元主导更新、其余逐渐失活，造成隐性的"神经元主导"（非真正的神经元死亡，但效果相近：部分神经元的实际贡献被边缘化）。

问题：如何在保留 Muon 正交化优势的同时，消除其神经元级不均衡问题？

解决方案：NorMuon（Neuron-wise Normalized Muon）在正交化之后增加逐行归一化（row-wise normalization），并为每个神经元维护独立的二阶动量统计（second-order momentum statistics，类似 Adam 的自适应学习率，但粒度到神经元而非整体），确保所有神经元的参数更新规模一致。

价值：在 1.1B 参数规模预训练实验中，NorMuon 比 Adam 训练效率提升 21.74%，比 Muon 提升 11.31%，显存占用与 Muon 持平。

未来方向：优化器改进与模型架构选择（MoE vs dense）、训练策略（课程学习、混合精度）的交叉影响是下一个值得实验的维度。

AlphaEvolve（Google DeepMind）：Gemini 驱动的代码 agent 已进入 Google 生产基础设施，训练速度翻倍，每年优化 15000 公里行程

现状：AlphaEvolve 最初作为算法发现工具发布，通过让 Gemini 不断生成、测试、演化代码来搜索更优秀的算法实现。这个方法在数学问题（如矩阵乘法算法）上已有成果，但实际生产应用尚待验证。

问题：能否把"通过代码演化寻找最优算法"的方法扩展到复杂的工程基础设施场景，并在真实生产环境中产生可量化的收益？

解决方案：Google 最新更新显示 AlphaEvolve 已被部署在多个生产场景：Google AI 训练基础设施优化（TPU/GPU 调度和内存布局），使大型模型的训练速度翻倍；分子模拟算法优化（加速材料科学研究）；自然灾害风险预测算法改进。Google Cloud 报告其路由优化功能每年减少约 15000 公里的冗余行程。

价值：AlphaEvolve 从"能找到更好算法"进化到"在生产中持续产生量化收益"，是 agentic AI 在真实工程场景规模落地的一个早期里程碑。

未来方向：代码演化 + 大算力搜索的组合能到达哪些人类工程师无法触达的优化空间，将成为下一批重要实验的主题。

Thinking Machines Lab 发布 Inkling：Mira Murati 团队首个自训练开源模型，975B 参数、多模态、百万 token 上下文

前 OpenAI CTO Mira Murati 创立的 Thinking Machines Lab 正式发布首款模型 Inkling。技术规格：975B 总参数 / 41B 活跃参数（Mixture-of-Experts 架构，即每次推理只激活其中一部分参数以降低成本），支持 100 万 token 上下文窗口，在 45 万亿 token 的文本、图像、音频、视频上预训练，具备原生多模态推理能力。模型全权重以 Apache 2.0 协议开源，可在 Hugging Face 下载，同日起在 Together AI、Fireworks、Modal、Databricks、Baseten 等推理平台上线。

团队的定位策略值得注意：Inkling 明确不追求跑分第一，而是把「可定制性」和「高效推理」作为核心差异化。John Schulman（联合创始人，前 OpenAI）透露，预训练从去年冬天便已开始。AINews 报道称，独立评测者认为 Inkling 是迄今最强的美国原产 Apache 2.0 开源模型，不过在部分 benchmark 上仍落后于顶级中国开源模型和闭源模型。同期还发布了 Inkling-Small（12B 活跃参数），供成本和延迟敏感场景使用。

xAI grok-build 开源后被证实：「改善模型」开关关掉仍在上传，整个 git 仓库含历史记录全部发送至云端

xAI 的命令行编程工具 grok-build 在 7 月 15 日以 Apache 2.0 协议开源，但开源本身带出了更大的问题。安全研究员的网络流量分析证实：grok-build 在运行时会将用户整个 git 仓库（含完整提交历史、已提交的密钥、SSH 密钥等）打包上传至 xAI 的 Google Cloud Storage 存储桶，上传数据量约为实际编程任务所需量的 27,800 倍。工具界面中「改善模型（Improve the model）」开关的描述具有严重误导性：关闭它仅意味着你的数据不被用于模型训练，并不阻止数据离开你的机器。Simon Willison 指出，开源后的代码库（84 万行 Rust）中，负责上传的代码仍然存在，只是被一个服务端下发的配置标志（`disable_codebase_upload: true`）在运行时关闭——xAI 随时可以在不更新客户端的情况下重新启用。

这是一个关于「技术上可以做到」和「用户被告知的」之间存在巨大鸿沟的典型案例。开源让社区看到了后门，但也暴露了 xAI 仍保留重新开启它的能力。

AI 方向观点

Every.to：你叠加的 Skills 正在让 frontier model 变蠢——49 个公开 skills 测试，只有 7 个真正有用

Every.to 的科技咨询负责人 Mike Taylor 提出了一个与主流「Skills 越多越好」的风气截然相反的判断：随着 frontier model 能力的跳跃式提升，你精心搭建的 skill 库很可能正在降低 AI 的表现。每个 skill 都是一份额外的指令，当模型本身已经「知道该怎么做」时，多余的 skill 会与模型的训练权重产生冲突，导致更多错误，还会大幅增加每次请求的 token 消耗。

研究数据支撑了这个判断。SWE-Skills-Bench（一个测试 skills 是否让 agent 更擅长软件工程任务的基准）评估了 49 个公开流传的 software engineering skills：39 个对性能没有任何影响，3 个让表现更差，只有 7 个带来了真正的提升。表现最差的 skill 让 token 消耗飙升了 451%，什么结果都没有改善。成功的 7 个 skills 都有一个共同点：它们提供了模型无法自行掌握的专属信息，比如财务风险计算公式或公司内部的交通调度规则。

Taylor 的结论：skill 的价值有保质期。当一个新版本的模型把你的 skill 所补丁的盲点内化为能力时，那个 skill 就从有用变成了有害。唯一不会过期的 skills，是那些给模型提供它不可能从公开数据中学到的东西：你的写作风格、公司模板、内部数据，或特定的工作流顺序。

49 个 skills 测了 39 个无用、3 个负优化。检查你的 skill 库，比新增 skill 更重要。

Garry Tan（Y Combinator CEO）：Skill files 最大的价值是可移植性，让你不必为换模型重写整套工作流

Garry Tan 在 X 上给出了一个和 Every.to 部分呼应、但重心不同的判断：skill files（以 Markdown 格式写成的可复用指令包）最重要的属性不是让模型更聪明，而是「可移植性」。他的逻辑是：当你的工作流被封装进一个独立于任何模型的 skill file，你就可以在 Fable 5、GPT-5.6 或未来某个新模型之间随时切换，而不必重写提示词、重建上下文。Skill files 是你的工作流资产，不是模型的附属品。

这和 Every.to 的批评并不矛盾：Every.to 说的是「不要用 skills 去补丁模型的通用能力」，Garry Tan 说的是「用 skills 去编码只有你自己才知道的私有工作流」。两者合起来其实是一条完整的建议：技巧不在于 skills 的数量，而在于 skills 的内容是否提供了模型无法自行学到的信息。

模型会换，工作流不应该每次都重建——这才是 skill files 真正值得投资的理由。

Boris Cherny（@bcherny）：自动化的真正价值，是让更多人能轻松参与贡献

Anysphere（Cursor 母公司）工程师 Boris Cherny 在 X 上发了一条影响广泛的思考：自动化最重要的意义，不是替代重复劳动，而是「让更多人可以轻松做出贡献」。他的具体语境是工程团队的基础设施文档——CLAUDE.md 文件、skills、Agent harness（运行 Agent 的脚手架：提示词、工具、测试框架的集合）等——当这些被写好，一个非工程师背景的同事，或者一个刚加入的新人，也能通过 Agent 完成原来只有资深工程师才能独自完成的任务。

自动化降低了贡献的门槛，但前提是有人先把知识和流程写进可被机器理解的文档里。这个「先写」的动作，本身就是竞争优势。

产品与商业

Dan Shipper（Every.to 创始人）：Granola CEO 谈 Codex-native app 的下一战场——主动提醒、而非被动回答

Dan Shipper 在 X 上发布了与 Granola（AI 会议记录应用）CEO 的深度对话记录。核心观点是：下一代 AI 产品的竞争焦点，不是「用户问、AI 答」，而是「AI 主动发现用户还没意识到自己需要的东西」——Granola 把这叫做「proactive features（主动功能）」，在用户没有触发的情况下，根据会议上下文主动生成待办、提醒或洞察。

Shipper 同时引用了一个更深层的概念：「Codex-native app（原生支持 Coding Agent 操作的应用）」——这类产品在设计上就预设了 coding agent 而非人类手指会直接操作它，UI 决策因此截然不同：更少视觉噪音、更多结构化输出、更清晰的可调用接口。他认为这是 AI 应用在设计哲学上最实质性的分叉点，而 Granola 正试图走在这条路上。

Proactive AI 不是更好的搜索框——它是把注意力管理外包给 AI。如果产品本身就能帮你注意到你该注意的，它在用户工作流中的地位就从工具变成了伙伴。

Peter Yang（@petergyang）：ChatGPT Live 和 Codex 两个强大产品互不交流，整合是下一个最大机会

产品负责人 Peter Yang 在 X 上指出了 OpenAI 当前最明显的产品摩擦点：ChatGPT Live（实时语音对话模式）和 Codex（AI 编程 Agent）是两个相互独立的产品，彼此没有工具调用（Tool Call，即 AI 在对话中主动调用外部服务或功能的能力）的集成——你用语音和 AI 交谈，但无法通过语音直接触发 Codex 去写代码、跑测试、提交变更。他的类比是：「需要一个钢琴踏板，踩下去就开启笔记本麦克风」——手动切换的摩擦感已经影响了实际使用。

这是产品整合滞后于能力扩张的典型症状：OpenAI 快速推出了多个强大能力，但这些能力之间的「管道」还没建好。Yang 认为，把 Live 和 Codex 打通，是当前成本最低、价值最大的产品决策。

能力的叠加不等于产品的提升——两个强大功能中间有摩擦，体验等于零。整合比新功能更难，因为它需要有人说「这件事没人做，但应该是我们做」。

AI 进展

Long-Horizon-Terminal-Bench：46 项长任务实测 agent 极限，当前最强模型成功率仅 15.2%

现状：现有 agent benchmark 大多是「短冲刺」任务——几分钟内完成、最终只看对错。这遮蔽了 agent 在真实工作中面对的核心困难：长时间规划、反复调试、环境摩擦和中途失败后的恢复能力。

问题：缺乏能评估 agent「走多远」而非「有没有到终点」的评测框架。一个在最后一步出错的 agent 和一个毫无进展的 agent，在 pass/fail 指标下毫无区别。

解决方案：Long-Horizon-Terminal-Bench 包含 46 项跨越 9 个类别的长任务（实验复现、软件工程、多模态分析、交互式游戏、科学计算等），每项任务最长允许运行 90 分钟，并以细粒度子任务打分（dense reward，即中间步骤也给分），而非只看最终结果。

价值：在 0.95 奖励阈值下，测试中最强的模型 pass@1 仅为 15.2%；要求完美完成时仅 10.9%。这意味着当前最强 agent 在 5 项长任务中有 4 项无法可靠完成。

未来方向：作者来自腾讯 HY LLM Frontier 和马里兰大学等机构，数据集已公开在 Hugging Face。该基准或将成为评估下一代 agent 系统长程规划能力的重要标尺。

arXiv 2607.08964 · HuggingFace Papers

GenCeption：视频生成模型即通用视觉学习器——用文生视频的 backbone 做深度估计、分割、姿态预测

现状：大规模文生视频模型（text-to-video diffusion models，即通过文字描述生成视频的扩散模型）在训练过程中积累了丰富的时空先验和视觉-语言对齐能力，这是传统视觉模型不具备的。

问题：这些能力至今主要用于生成内容，而非视觉感知任务（如深度估计、表面法线预测、相机位姿估计等）。

解决方案：GenCeption 把预训练好的视频生成扩散模型的 backbone 直接迁移，通过文本指令引导它完成感知任务，而非生成任务，无需从头训练专用感知模型。

价值：在深度估计、表面法线、相机位姿估计、分割和 3D 关键点预测等任务上达到 state-of-the-art 水准，多项超越专用模型。这验证了「生成式预训练 → 感知任务迁移」的范式可行性。

未来方向：如果视频生成模型成为通用视觉基础，那么花在生成能力上的算力，也在为机器人、自动驾驶、AR 等感知任务投资——两用性大幅提高了预训练的投资回报。

arXiv 2607.09024 · HuggingFace Papers

AgentAbstain：LLM agent 知道「何时不该动手」吗？263 对任务测试，结果不乐观

现状：当前 agent 评测集中测试「agent 能做什么」，而非「agent 知不知道什么时候不该做」。过度行动（over-action）——在不应该执行操作时仍然执行——可能比失败更危险。

问题：缺乏专门测试 agent 「克制能力」的基准。一个 agent 能正确完成任务，但如果它在任务条件不满足时也强行执行，它就是不安全的。

解决方案：AgentAbstain 包含 263 组配对任务，跨越 42 个可执行沙盒环境。每组由一个「应该执行」的任务和一个通过受控变化（指令、工具状态或环境状态改变）派生的「应该克制」的配对任务组成。

价值：测试结果表明，当前主流 LLM agent 在「应该克制」的情境下仍然倾向于行动，辨别「何时不动」的能力显著弱于「如何动」。

未来方向：这对 agent 在生产环境的部署有直接含义：给 agent 更强的能力之前，需要先给它更好的「停下来」的判断力。

arXiv 2607.10059 · HuggingFace Papers

Embodied.cpp：跨异构机器人的具身 AI 推理运行时，VLA 模型部署成功率达 100%

现状：具身 AI（Embodied AI，指能感知环境、进行决策并控制物理实体的 AI 系统）目前面临严重的部署碎片化问题：不同机器人、不同芯片、不同操作系统，每种组合都需要单独的部署工程。

问题：VLA 模型（Vision-Language-Action model，即同时理解视觉输入、语言指令并输出动作的模型）和世界-动作模型（WAM）缺乏统一的跨平台推理运行时。

解决方案：Embodied.cpp 是一个用 C++ 实现的可移植推理运行时，通过五层抽象（输入适配器、序列构建、骨干执行、头部插件、部署适配器）统一处理不同机器人和模拟器的部署需求，实现一套代码多平台运行。

价值：在闭环控制实验中，VLA 模型部署成功率分别达 100% 和 91%；WAM 的模块内存占用从 312.2 MiB 降至 88.1 MiB（减少 72%）。

未来方向：随着工厂和物流场景加速引入具身 AI，统一运行时层正在成为基础设施标准件。

arXiv 2607.02501 · HuggingFace Papers

KronQ：Kronecker 分解 Hessian 量化——让 LLaMA-3-70B 在 2-bit 权重下稳定运行

现状：模型量化（Quantization，即把模型的浮点数权重压缩为低比特整数表示，以降低显存和推理成本）是让大模型在消费级硬件上可用的关键路径。但极低比特（2-bit）量化至今是公认的难题：现有方法在 LLaMA-3-70B 规模下要么精度崩溃，要么产生无意义输出。

问题：主流量化方法（GPTQ、GPTAQ 等）在确定「哪些权重对输出影响更大」时，没有充分利用梯度协方差信息，导致在 2-bit 时误差累积失控。

解决方案：KronQ 使用 Kronecker 分解 Hessian 近似（一种用于估计模型参数重要性的数学工具）来权衡不同输出通道的重建优先级，使量化误差更均匀地分布，而非集中在少数关键权重上。

价值：在 LLaMA-3-70B 的 2-bit 权重量化下，KronQ 实现了 7.93 困惑度（Perplexity，语言模型评估指标，越低越好），而 GPTQ 和 GPTAQ 在同等条件下直接发散或输出退化。论文已被 COLM 2026 接收。

未来方向：2-bit 推理如果成熟，70B 量级模型有望在单张消费级显卡上运行——这将根本性改变开源模型的可及性。

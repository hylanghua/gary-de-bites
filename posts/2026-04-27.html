AI 方向观点

Guillermo Rauch（Vercel CEO）：Coding Agent 是通往超级智能自我改进的地基

Rauch 在 X 上发了一段延伸讨论，核心是：Coding Agent 不只是效率工具，而是超级智能（superintelligence，即远超人类能力的 AI）的必要前提。理由是自我改进能力依赖代码生成，只有能写出比自身更好代码的 Agent，才可能启动真正的能力自举。这个论断背后有 Vercel 自身数据支撑：他们平台上 30% 的应用已经由 Agent 直接生成，年化收入从 2024 年初的 1 亿美元增长到 2026 年 2 月的 3.4 亿美元，增长飞轮已经形成。

Rauch 此前说过一句话值得并排来看：「代理会让定制软件比购买现成软件更快。」这两个判断合在一起描述的是同一件事：软件生产的单位成本正在跨越某个拐点，超过这个拐点后，Agent 自建比外采更快，那么软件分发与软件生产的经济学都要重写。Vercel 的 IPO 准备信号恰好在这个时间点出现，不是巧合。

Rauch 把 Coding Agent 描述为超级智能的脚手架，而不是目的本身，这是目前少有人说清楚的一步。

Sam Altman：是时候认真重新设计操作系统和用户界面了，人和 Agent 需要同等可用

Altman 在 X 上写道：「感觉是认真重新思考操作系统和用户界面设计的好时机（互联网也是）；应该有一个对人和 Agent 同等可用的协议。」这句话说的是一个目前还没人专门做、但越来越急迫的问题：现在所有的 OS 和 Web 协议都为人类交互设计，Agent 只能通过模拟鼠标点击、截图理解、HTML 解析等绕路方式操作，既低效又脆弱。

如果一个新协议真的出现，它意味着从 HTTP 到应用层的接口都需要重写，软件架构的「能被 Agent 调用」将成为和「能被人用」同等重要的一维设计要求。这件事现在还是一个开放问题，但说出这句话的是 Sam Altman，而且是在 GPT-5.5 发布、Agent 能力刚出现明显跃升的节点上说的。

Altman 不是在描述一个产品，是在描述一场基础设施层的需求，目前只有问题，没有答案。

产品与商业

Anthropic「项目交易」：Claude Agent 完成 186 笔实物交易，Opus 谈价更好但用户感知不到

Anthropic 在 2025 年 12 月对内部 69 名员工做了一个真实货币实验：每人 100 美元预算，全程由 Claude Agent 代为买卖，真实货品在谈判成功后实际交换。Agent 通过专属 Slack 频道完成挂单、出价、议价、成交，最终促成 186 笔交易，总交易额超过 4000 美元——从单板滑雪到一袋乒乓球。

最值得关注的是模型质量实验：Anthropic 悄悄将用户随机分配给 Claude Opus 4.5 或 Haiku 4.5（两者推理能力差距明显），结果发现 Opus 卖家每件多赚 2.68 美元，Opus 买家每笔省 2.45 美元，Opus 用户平均多完成 2.07 笔交易。但被 Haiku 代理的用户在交易公平感评分上几乎与 Opus 用户持平（4.06 对 4.05），几乎察觉不到自己在博弈中处于劣势。Agent 代替人谈判已经到来，但不是所有 Agent 的能力都一样，而用户通常看不出差距。

Anthropic 证明了 Agent 商务谈判的可行性，顺带揭示了一个结构性风险：被较差 Agent 代表的用户会系统性地亏钱，却没有任何感知。

Every.to：你才是最贵的模型，AI Agent 真正的成本是你盯着它的时间

Every.to 本期主题：「The real cost of AI agents is your time.」（AI Agent 的真实成本是你的时间。）这个论断直接打穿了一个普遍误解，即为什么我的 API 账单这么高。账单是显性成本，但真正的瓶颈是你花在启动任务、检查中间结果、纠正偏差上的注意力。每次你决定「让 Agent 再跑一次」还是「我来改」，都在消耗你的判断力，而判断力是不可扩展的。

框架的核心是区分哪些任务可以真正放手（Agent 可以犯错并自我修正，结果可逆），哪些任务需要人持续盯着（结果不可逆、错误代价高）。这不是「AI 够不够聪明」的问题，而是「这类错误的代价和发现窗口期」的问题。Every 的结论是：先做任务映射，再决定是否让 Agent 接管。

当所有人都在问「这个 Agent 能做什么」，Every 问的是「你盯着它要花多少时间」，这才是正确的 ROI 计算框架。

Garry Tan（YC 总裁）：用 SOUL.md / USER.md / AGENTS.md 给 Agent 注入持久身份与规则

Garry Tan 分享了他给自己的 Agent 配置「身份文件」的做法：SOUL.md 定义 Agent 的性格和价值观，USER.md 描述使用者是谁、偏好和习惯，AGENTS.md 规定 Agent 之间协作的规则和权限边界。这三个 Markdown 文件放进工作目录，Agent 在每次对话时都能读取，形成跨对话的持久上下文（persistent context，即不随对话结束而消失的记忆）。

这套做法本质上是把「谁在做事、为谁做事、规则是什么」结构化地写下来，让 Agent 不再是每次从零开始的工具，而是有稳定身份的协作者。Tan 的 OpenClaw 在这套配置下甚至会在晚上 12:30 后拒绝回复，因为他在 USER.md 里写了健康目标。

SOUL.md / USER.md / AGENTS.md 是目前最具可操作性的 Agent 个性化方案，不需要修改模型，只需要修改上下文。

人文与哲学

纯银：AI 时代坐电梯上升的集体幻觉

纯银这期的核心问题是：如果擅长用 AI 之后你的产出大幅提升，那你的竞争力是什么？他的答案是：价格不是由价值决定的，价格是由竞争决定的。AI 赋能有很强的「点石成金」体感，但这种体感是个陷阱，因为当每个人都同样被提升，你相对于竞争对手的位置并没有改变，只是整体市场的效率门槛被拉高了。

他援引了娱乐圈从业者的观察：行业里每个人都在卷，卷到最后价格被压下去，只有少数头部留住了溢价。AI 时代的竞争逻辑与此相似，AI 是「电梯」，把楼层基准线整体抬高，但抬高不代表你在这栋楼里的位置更高。真正的竞争优势，来自你在 AI 均匀提升所有人之后还剩下的那部分差异。

纯银说的不是 AI 没用，而是「AI 赋能的体感」和「竞争优势的实质」是两件事，混淆它们才是危险所在。

AI 进展

MultiWorld：多智能体多视角视频世界模型（arXiv 2604.18564）

现状：当前主流视频世界模型（video world model，即用视频预测来模拟环境的模型）默认只有一个 Agent 在环境里行动，无法处理多个 Agent 同时存在、互相影响的场景。

问题：多玩家游戏和多机器人协作等场景需要模型同时追踪多个 Agent 的动作，并保证不同视角（camera views）之间的观察一致性，单 Agent 架构根本无法扩展到这里。

解决方案：香港大学团队提出 MultiWorld，引入 Multi-Agent Condition Module 控制每个 Agent 的独立动作，用 Global State Encoder 保证多视角观察的全局一致性，多视角并行合成，不随 Agent 和视角数量增加而线性变慢。

价值：在多人游戏和多机器人操控两类场景上验证，动作可控、视角一致，为具身 AI（embodied AI，即在物理或仿真环境中行动的 AI）训练提供了更真实的多体仿真基础。

未来方向：扩展到更大规模的真实世界机器人集群任务，以及和强化学习框架结合做多 Agent 策略训练。

arXiv 2604.18564

SkVM：将 LLM Skills 当代码编译，跨模型跨 Harness 可移植（arXiv 2604.03088）

现状：AI Agent 的「技能」（skill，即预定义的能力模块，如「发邮件」「查日历」）被当作普通文本上下文注入给 LLM，同一个技能在不同模型上行为不一致，换一个 agent harness（运行 Agent 的框架，如 AutoGen、LangGraph）又要重写。

问题：技能无法跨模型、跨平台移植，类似早期软件没有操作系统的状态，每个程序都要为每台机器单独编写。

解决方案：上海交通大学团队提出 SkVM，把技能视为代码，在编译时做能力分析、环境绑定、并发抽取，运行时做 JIT 固化（just-in-time solidification，即将反复使用的技能模式缓存为确定性代码以降低推理开销）和自适应重编译。

价值：在 8 个不同规模 LLM 和 3 个 Agent harness 上评测，减少 token 消耗最多 40%，最高 3.2 倍速度提升，通过 JIT 固化达到 19-50 倍延迟降低，且任务完成率提高。

未来方向：将 SkVM 推广到更多 Agent 框架，以及探索技能市场（skill marketplace）生态。

arXiv 2604.03088 · HuggingFace Papers

MTA-Agent：首个多模态深度搜索 Agent 开源配方（arXiv 2604.06376）

现状：当前「深度搜索」（deep search，即 Agent 自主发起多轮搜索并综合信息的能力）Agent 几乎全是纯文本的，只检索文字，忽略图像。

问题：真实世界的信息大量以图文混合形式存在（产品图、论文图表、地图截图），纯文本 Agent 只能处理一半的知识库。

解决方案：MTA-Agent 提出完整的多模态深度搜索 Agent 方案，支持动态图文并行检索。文中提到 MMSearch-R1 通过强化学习训练 Agent 在搜索时自主决定是否需要检索图像，实现真正意义上的图文混合深度搜索。

价值：提供了开放的配方（open recipe），团队把实现细节完整公开，任何团队都可以复现和扩展，对需要处理图文混合信息的知识库 Agent 有直接参考价值。

未来方向：扩展到视频检索，以及与多跳推理（multi-hop reasoning，即需要多步信息拼接才能回答的问题）结合。

arXiv 2604.06376

LLM Agent 工具调用进化图谱：从单工具到多工具编排（arXiv 2603.22862）

现状：LLM Agent 的工具调用能力（tool use，即让模型能调用外部 API 或执行代码的能力）已从早期的单次调用演进到复杂的多工具并行编排，但这个演进过程缺乏系统性梳理。

问题：如何评估和比较不同系统的工具调用能力，目前没有统一的分类框架和评测维度。

解决方案：本文围绕六个核心维度系统整理文献：推理时规划与执行、训练与轨迹构建、安全与控制、资源约束下的效率、开放环境中的能力完整性、benchmark 设计与评测，并指出线性推理流程已向原生推理时计算和 MCP（Model Context Protocol，即模型上下文协议，一种让模型与外部工具通信的标准）等开放标准演进。

价值：为 Agent 工程师提供了选型、评测和规划下一步的系统参考图，对做 Agent 工具链设计的团队有直接参考价值。

未来方向：探索工具调用能力的自动化评测框架，以及更复杂的跨工具编排基准。

arXiv 2603.22862

MemOS：为 LLM 设计的记忆操作系统，像 OS 管进程一样管记忆（arXiv 2505.22101）

现状：LLM 的「记忆」目前分散在三层：参数记忆（parametric memory，训练时压进权重的知识）、激活态记忆（activation memory，对话上下文窗口内的临时状态）和外部检索（RAG，即检索增强生成，通过查外部数据库补充知识）。三层各自独立，没有统一管理。

问题：跨对话的长期记忆、任务间知识复用、多模态记忆整合，都没有系统性解决方案，导致 Agent 「用完就忘」，无法积累经验。

解决方案：MemOS 提出 MemCube 作为统一记忆抽象（memory abstraction），可追踪、融合、迁移三类记忆，并引入操作系统级的治理机制：调度、分层、API 抽象、权限控制和异常处理。

价值：为持续学习（continual learning）和长期运行的 Agent 系统提供了基础设施层方案，对构建有「记忆」的 Agent 的团队有直接参考价值。

未来方向：将 MemOS 与主流 Agent 框架集成，以及探索多 Agent 共享记忆池的协作场景。

AI 方向观点

Aaron Levie（Box CEO）：管 AI 要管应用场景，不是基础模型

Levie 直接回应 Fable 5 封禁事件："管理模型本身非常困难——AI 能力的排列组合近乎无限，在每次模型发布前建立一套客观、普适的指标几乎不可能，需要反复的博弈、研究和政策谈判。把同样的流程扩展到每个国家、每次发布，你很快就能看到 AI 进步会被拖慢到什么程度。"他的结论是：监管力量应该聚焦在 AI 的具体应用场景上，那才是风险真正出现的地方，而不是模型本身。

这个逻辑有道理，也有盲点：应用层监管确实可操作性更强，但高危能力（如精确的漏洞挖掘）在模型层面就已存在，应用层的门槛拦不住拥有直接 API 访问权限的人。Levie 给的是正确的方向，但"管应用"和"管模型能力上限"并不互斥。

Satya Nadella：Loopcraft——"你可以外包任务，但永远无法外包学习"

微软 CEO Satya Nadella 在 X 发表长文《A frontier without an ecosystem is not stable》，28 小时内突破 6000 万浏览。核心论点：AI 时代的竞争不在于用哪个模型，而在于每家公司能否建立起自己的"学习闭环（learning loop）"——人力资本（员工的判断、关系、创意）和 token 资本（企业拥有的 AI 能力）相互叠加、持续复利。"这是第一次，我们可以在人和数字系统之间创造真正的认知闭环，"他写道，"而这从根本上改变了我们对企业内部工作的理解。"

Nadella 还对纯粹的"模型竞赛"叫停：他认为一个"少数模型吃掉所有价值"的世界对 Microsoft 不利，真正稳定的生态要让每家公司、每个行业都能拥有并积累自己的 AI 资产。这既是他对 OpenAI 分手后 8 个月的首次清晰战略表态，也是 Big Model vs Big Harness 争论中，他旗帜鲜明地站到了"建平台、建生态"那一边。Satya 把"学习闭环"变成了新时代的护城河理论，这比说"我们支持开放 AI"要锋利得多。

Latent Space AINews · BusinessToday

Guillermo Rauch（Vercel CEO）：sandbox / function / server / build 本质是同一套 compute

Rauch 在 X 连续发帖阐述他对 compute 基础设施的判断："一个 sandbox、一个 function、一个 server、一次 build——你明白了吗？这些都是同一套底层 compute 基础设施的不同表达，只是在负载均衡、并发、持久化、overcommit（过度分配资源以提升利用率）参数上做了调整。"他宣布 Vercel 函数运行时上限大幅延长，背后是历时数年自研的 microVM（微型虚拟机）Fluid Compute 基础设施，已先后支撑了 Builds、Sandbox 和 Functions。

这是 Vercel 在基础设施层面的最强一次公开表态：从托管平台升级为 compute provider，和 AWS Lambda 的竞争正在变得直接。Vercel 用自研 microVM 把 serverless 的弹性和服务器的持久性融合在一起，2026 年终于有了可信的答案。

Hoop 创始团队：三位非工程师，10 小时建了一个 Agent-native 内部分析工具

Every.to 本期刊发了 Hoop 联合创始人 Stella Garber 的实操记录。Hoop 是一个帮助订阅制品牌降低流失率的 AI Agent；创始团队五人中没有传统意义上的工程师。他们用 Claude API、Next.js 和 Supabase，在不到 10 小时内搭建了一套内部客户访谈分析工具：上传 Zoom 录音，自动跑四五条提示词，生成按 PULL 框架（Harvard Business School 的早期 PMF 验证框架）打分的结构化洞见，并把每位潜在客户的所有对话汇总成单一时间线。

这个工具有两个值得注意的细节。一是设计先行：负责产品的 Justin 先把 UI 做对，再接数据——他认为工具"如果不好看，团队就不会用"。二是关键决策点：提示词质量必须比个人用 Claude 更好，否则无法说服团队放弃各自的工作流。结果这套工具不只提升了内部效率，还反过来重塑了产品本身的迭代节奏，原来需要主观解读的客户信号，现在变成了客观追踪的周度指标。Agent-native 工具建设的门槛已经低到：核心是提示词质量，而不是工程能力。

Peter Steinberger（PSPDFKit 作者、OpenClaw 创始人）：clawsweeper — GitHub issue 自动变 PR

Steinberger 描述了他们在开源项目上搭建的 Agent 工作流：每当有人在仓库提 issue，@clawsweeper 就会自动 review，判断 issue 是否符合 VISION.md（项目愿景文档，即"产品北极星"），如果符合，就自动创建 PR 并完成 code review。整个 issue-to-merge 流程无需人工介入。

这不是 demo，而是在真实开源仓库跑起来的生产 Agent。它回答了一个 PM 会反复问的问题：Agent 在软件工程流程里的最小落地单元是什么？答案是：从单条触发事件（issue）到单个输出（PR），有 VISION.md 做约束，有 code review 做质控。clawsweeper 把 Agent 变成了开源项目的隐形维护者，比招一个兼职维护员便宜，比没人维护强太多。

TLDR 精选了一篇题为《The Web We Know Is Going to Disappear》的长文，论点直白：网络正在从"人类搜索、点击、阅读、发现"的开放空间，变成"AI 聊天界面背后的数据基础设施"。搜索引擎的流量分发逻辑正被 AI 聊天接口替代，网站越来越多地是为机器而建，而不是为人。

AI 进展

Ramp：产品工程 Workflow 下 Agent 完成率从 100% 崩至 20%，成本差 2525 倍

现状：现有 benchmark（基准测试）主要评估孤立任务，无法反映 Agent 在真实串行 workflow 中的表现。

问题：在依赖前一步输出的生产级工程任务链中，Agent 的错误会级联扩散，早期失误让后续所有阶段都无法完成。

解决方案：Ramp 以编译器构建任务为测试床，组织成上下文和中间产物跨步骤持续传递的串行依赖链，并引入"复活协议"——某步失败后允许 Agent 继续评估后续步骤，以提高诊断精度。

价值：对 15 个主流模型的测试发现：任务完成率从第一阶段的 100% 逐步崩溃到最后阶段仅 20%，无任何模型完整通过整条流水线；性能相近的模型之间，计算成本差距高达 2525 倍。

未来方向：评估体系需要转向"运行时可观测、生产场景接地气"的持续评估，而非快照式单任务跑分。

arXiv 2605.27492

BAGEN：LLM Agent 的预算盲区——前沿模型持续烧没有希望的任务

现状：LLM Agent 的成本控制通常是事后统计，而非主动感知。

问题：前沿模型对预算（token 消耗上限）普遍过度乐观：在几乎不可能完成的任务上持续投入算力，而不是主动提前告警。能力强的模型和预算感知能力之间的相关系数（r）仅 0.35。

解决方案：BAGEN 把"预算感知"形式化为逐步区间估计——每一步预测剩余预算的上下界，超出置信区间时主动告警。通过 SFT（监督微调）+ RL（强化学习）训练早停和告警行为。

价值：在失败任务上，早停机制可节省 28–64% 的 token 消耗；但精确区间校准仍是难点，经过 SFT+RL 后覆盖率最高只达 47%。

未来方向：预算感知应成为 Agent 基础能力之一，和工具调用、记忆管理并列。

arXiv 2606.00198

General AgentBench：Test-time Scaling 在 3–7 轮触顶，上下文污染是主因

现状：Test-time scaling（推理时扩展，即让模型在推理阶段花更多计算）被认为是提升 Agent 能力的重要手段。

问题：顺序扩展（多轮交互）在通用任务上 3–7 轮达到性能峰值，此后上下文累积带来"污染"，性能反而退化；并行扩展（多轨迹采样）虽然理论上限更高，但模型自我选择无法弥合"验证缺口"。

解决方案：General AgentBench 建立了跨搜索、编程、推理、工具调用四类任务的统一评估框架，对 10 个主流 Agent 进行了系统评测。

价值：SWE-bench 或 GAIA 高分不能预测跨领域鲁棒性——专项跑分和通用能力之间存在显著断层。

未来方向：Agent 的 test-time compute 上限更多受制于上下文管理策略，而非计算量本身。

arXiv 2602.18998 · HuggingFace Papers

SlopCodeBench：迭代越多代码越烂，11 个模型无一完整通关

现状：现有编程 benchmark 主要考察"单次给完整需求，能否一次通过测试"，不考察代码质量的长期演化。

问题：在反复迭代、需求持续演变的场景中，Agent 生成的代码会出现两种系统性退化：冗余代码比例上升（verbosity）、高复杂度函数占比扩大（structural erosion，即结构性侵蚀）。代码能通过测试，但越来越难以扩展。

解决方案：SlopCodeBench 设计了 20 个问题、93 个检查点，强迫 Agent 在不断演化的规格下扩展自己此前生成的代码，且不规定内部结构，以测量真实架构决策能力。

价值：最高检查点解决率仅 17.2%，无模型从头到尾完整通关；迭代压力下，所有模型都在降低代码质量。

未来方向：代码质量维度（架构可扩展性、技术债）应纳入 Agent 评测核心指标，"通过测试"不等于"写出好代码"。

arXiv 2603.24755 · HuggingFace Papers

SWE-Factory：多 Agent 流水线自动构建代码评测环境，每实例成本 $0.047

现状：构建代码 benchmark 需要为每个 GitHub issue 手动搭建评测环境、编写测试判断器，极度耗时费力。

问题：人工构建的高成本限制了训练数据和评测集的规模，成为代码 Agent 能力提升的瓶颈。

解决方案：SWE-Factory 的核心是 SWE-Builder，一套由四个专项 Agent 组成的协作循环，自动完成环境配置；配合标准化的 exit-code 判分法（用程序退出码判断测试是否通过，无需人工写解析器），F1 值达 0.99。

价值：在 671 个真实 GitHub issue（跨 Python / Java / JavaScript / TypeScript）上，GPT-4.1 mini 成功构建 337 个有效评测实例，单实例成本 $0.047；比人工方式快几个数量级。

未来方向：大规模自动化构建评测数据集，可能是突破当前代码 Agent 能力瓶颈的关键基础设施。

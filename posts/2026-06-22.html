Sakana AI Fugu：7B 协调模型指挥 GPT-5、Claude、Gemini，SWEBench Pro 73.7 与 Fable 5 并肩

日本 AI 实验室 Sakana AI 今日发布 Fugu 和 Fugu Ultra 系统。核心不是一个大模型，而是一个 7B 参数的 RL Conductor（通过强化学习训练的调度器），它不直接生成答案，而是分析任务类型，把子任务分发给 GPT-5、Gemini 3.1 Pro、Claude Opus 4.8 等顶级模型，再汇总并校验输出。Fugu Ultra 在 SWEBench Pro（评测模型在真实软件工程任务上的权威基准，满分 100）上拿下 73.7 分，在 TerminalBench 上达到 82.1——超越 GPT-5.5 和 Claude Opus 4.8，与 Claude Fable 5 和 Mythos Preview 并肩。

Aaron Levie（Box CEO）对此的评价点出了更大的技术意涵："Sakana released a model that effectively orchestrates all the other models。" 这句话的潜台词是：在顶级闭源模型已趋于同质化的当下，"如何调度和组合这些模型"正在成为一个独立的、可训练的能力维度。Sakana 没有在参数量上竞争，而是在"怎么用别人的模型"上训练出了边界。Fugu 证明了一个新的可能：前沿性能不必来自千亿参数，一个 7B 的指挥官有时候比一个 7000 亿的孤独天才更有用。

Guillermo Rauch（Vercel CEO）：编程 Agent 会把 IKEA 效应榨干你，如果你让它的话

Rauchg 今日写下一句话警告："Coding agents will squeeze every ounce of IKEA effect out of you, if you let them。" IKEA 效应（IKEA effect）是行为经济学中的概念，指人们会对自己亲手参与创造的东西产生远超客观价值的依恋感——你花两小时组装的书架，比花同样钱买的成品更让你满意。Rauchg 说的是：当 Agent 把所有代码都写好了，那种"我做的"的感觉随之消失，你开始对结果漠然，或者把本不该干预的东西改回来。

他同日也分享了 Vercel 的业务数据作为背景：六个月前 Vercel 的部署中不到 3% 由 coding agent 触发，到 2026 年 6 月 17 日这一比例已超过 50%。Vercel.com 本身也在同期完成了一轮性能全面优化——"凡是光照到的地方都被优化了"——暗示这是 Agent 主导下的工程加速。Rauchg 的警告说的不是 Agent 能力不够，而是人类心理还没准备好：失去掌控感的创造者，比从未参与的旁观者更难受。

纯银：结构性困境不能在原结构里修，长板策略才是真正的出路

纯银在今日的小报童专栏里提出了一个值得反复琢磨的产品与人生框架：结构性困境（structural dilemma）的意思是，有些缺陷之所以难以修复，是因为它和整个结构的支撑性因素强耦合——盈亏同源，缺陷本身就是结构的组成部分，修缺陷等于改结构，改结构等于重建。他的例子是新浪：新浪门户遇到结构性困境，没有在原有结构里死磕，而是靠投资微博建立了新结构，从而迂回解决了问题。微博今天遭遇的停滞，也正是因为多年没有新的增长带动，被困在旧结构里。

针对这个问题，他提出了比 SWOT 分析实操性更强的"长板策略"：第一步识别长板（团队和产品的真正优势是什么）、红线（一踩就死的雷区）、短板（其中哪些有改进思路，哪些没有）；然后把 50% 以上的注意力压在长板上，把守住红线的资源单独划拨出来，剩下的用于日常运营和有改进思路的短板。"没有改进思路的短板，尽量不要去想它，勿自添烦恼。"

这个框架的核心洞察是：长板延伸到一定程度，会建立新的结构——这时候很多短板要么有了新解，要么变得不再重要。互联网公司惧怕增长停滞，本质上也是因为只有增长才能带来建立新结构的资源和空间。纯银说的是一件无论对产品还是对个人都成立的事：绕不过去的困境，往往不是靠正面攻克，而是靠把自己最强的部分拉到足够长，再回头看的时候困境已经不在了。

Paul Graham：十亿美元不是奇迹，是 15% 月增长持续五年的数学结果

Paul Graham 本月在牛津大学做了一次演讲，文章版随后发布在他的个人网站，并被 Wisereads 本周选为最多高亮文章第一名。他的核心论点是对"一个人不可能合法赚到十亿美元"这一政治断言的数学反驳：十亿美元不是一个道德问题，而是两个变量的乘积——增长率和增长可以持续多久。如果月增长率 15%，持续五年，收入会变成原来的 4384 倍；从每月 $1 万到每月 $4400 万，在正常的创始人持股比例下，这就是一个十亿美元公司的路径。

Graham 没有停在数学上。他的深层观点是：指数增长的结果看起来"不可能"，是因为人类直觉不擅长理解指数——这和那些把天价科技公司财富解读为"作弊"的政客，犯的是同一个认知错误。要实现这个数学，需要的不是作弊，而是建造一个用户喜欢到会主动推荐的产品，加上一个足够大的市场让增长能持续。Graham 提供的是一个简洁的反叙事：你所见到的最大的财富，通常不是权力游戏的产物，而是算术的产物——只不过那是没有人教过普通人的那种算术。

Contagion Networks：多 Agent 评审系统里，偏见像传染病一样跨 Agent 扩散

现状：多 Agent LLM 系统（即多个 AI 相互协作完成推理、代码生成或任务执行的架构）被广泛用于生产环境，包括让多个 Claude 或 GPT 实例互相评审输出。这一架构在提升性能的同时，也引入了一个新的可靠性问题：当一个 Agent 出现偏见时，这个偏见会如何影响其他 Agent？

问题：直觉告诉我们"多个 Agent 打分比单个更可靠"，但这个假设成立的前提是各 Agent 的判断相互独立。如果偏见能在 Agent 之间传播，那群体评分可能比单点更不可信，因为错误会被放大。

解决方案：论文引入"Contagion Networks"（偏见传染网络）框架：在 Agent 组成的系统中，偏见以类似传染病扩散的方式在 Agent 间流动——通过提示、共享上下文或对话历史传播。研究发现，当一个 Agent 产生错误判断后，其余 Agent 暴露于这个判断时，会以高于随机的概率"被感染"，产生相似的错误。

价值：为多 Agent 评审系统的可靠性设计提供了理论基础——偏见隔离（每个 Agent 独立、不共享先前 Agent 的输出）可能比连锁评审更安全。

未来方向：多 Agent 系统的可信度评测需要纳入"偏见传染"这一维度，Agent 独立性设计将成为企业级多 Agent 部署的标准考量。

EpiBench：首个针对多模态 Agent 多轮研究工作流的系统性基准

现状：多模态 Agent（可以处理图像、文字、数据表格等混合信息的 AI 系统）在研究类任务中的实际表现，缺乏系统性的评测标准。现有基准大多测单轮问答，无法捕捉"连续多步推进一个研究问题"这种更接近真实工作的场景。

问题：研究类工作流天然是多轮的：先规划（planning）信息来源，再搜索（search）和提取，最后综合（synthesis）形成结论。这三个阶段的任何一步出错，都会导致最终输出失效，但现有评测无法精确定位是哪一步出了问题。

解决方案：EpiBench 设计了覆盖完整研究工作流的评测套件：任务要求 Agent 在多轮交互中依次完成规划→搜索→综合，每个阶段均有独立的评分维度，支持跨模态信息处理（文字、图像、图表）。

价值：第一次让"多模态 Agent 做研究"这件事有了可量化的性能参照，PM 和研究员可以借此比较不同 Agent 框架在哪个阶段出问题最多。

未来方向：多轮、多阶段的研究任务评测将取代单轮问答基准，成为评判 Agent 实用性的主流标准。

Claude Mythos 扫描 Firefox：271 个 bug 含一个潜伏 15 年的漏洞，AI 安全管道进入新时代

现状：Mozilla 在 2026 年 4 月启动了一条基于 Claude Mythos Preview 的自动化安全扫描管道（agentic harness，即能自主生成测试用例并验证 bug 是否可复现的 Agent 系统），用于扫描 Firefox 源代码中潜在的安全漏洞。Lenny's 播客今日专门制作了相关内容，标志着这个案例已进入 AI 能力的"教科书级"讨论。

问题：传统 fuzzing（模糊测试，即随机或半随机地向程序输入数据，观察是否崩溃的测试方法）虽然运行了多年，却无法覆盖那些需要跨越代码库多个部分、精确组合特定边界条件才能触发的复杂漏洞。一个藏在 Firefox <legend> 元素里的 bug 就这样躲过了十五年的人工审计和自动化测试。

解决方案：Claude Mythos 管道的关键不是"找到更多崩溃"，而是"自动构建可复现的测试用例"——找到一个可疑路径后，Agent 自动验证它是否真的能触发，不能复现的会被自动过滤，可复现的才上报。这让每日处理几千个候选 bug 成为可能。

价值：4 月单月，Mozilla 共修复 423 个安全漏洞，其中 271 个直接归因于 Mythos 管道（180 个 sec-high，80 个 sec-moderate）。那个 15 年的 <legend> bug 是象征性的：AI 找到了人类视觉和直觉无法找到的东西。

未来方向：AI 自动安全扫描将成为大型开源项目的标配基础设施，"AI 每天找到的 bug 数量"将成为衡量代码库安全度的新维度。

FactCheck：在预判长程动作前先验证可行性——多 Agent 协作框架

现状：LLM Agent 在执行长程任务（long-horizon task，即需要多步骤推理和规划的任务，如管理一个日程、完成一个工程项目）时，经常规划出无法在现实中执行的动作序列——因为模型没有在行动前验证"这个动作在当前状态下是否可行"。

问题：现有多 Agent 动作预判框架大多只关注"最可能发生什么"，不关注"这件事在当前约束下是否真的能发生"——导致 Agent 计划了一系列在逻辑上顺畅但现实中不可行的动作链。

解决方案：FactCheck 在多 Agent 协作框架中引入"可行性感知"（feasibility-aware）模块：每一个规划步骤在执行前，先由专门的验证 Agent 检查当前状态下该动作是否真的可以被执行。同时整合了多模态信息（视觉、音频、文字），支持跨模态的长程推理。

价值：让 Agent 规划系统第一次有了"先想清楚能不能做，再想怎么做"的内置审核层，减少了在不可行路径上浪费的推理资源。

未来方向：可行性验证将成为所有生产级 Agent 规划器的标准前置步骤，尤其在物理世界 Agent（机器人、自动化流程）中作用更为关键。

FastContext：把仓库探索和代码生成分开训练，coding agent 降 token 消耗、提升解题率

现状：大多数 coding agent（代码生成 AI Agent）在处理大型代码仓库时，把"探索代码库找到相关上下文"和"基于上下文生成代码"混在同一个模型里完成。这导致 agent 不得不在探索阶段消耗大量 token 来读取大量不相关文件，影响效率和准确性。

问题：代码库探索（repository exploration）和代码修复（code solving）是两种截然不同的认知任务：前者需要广度优先的导航和快速相关性判断，后者需要深度专注于具体代码逻辑。用同一个模型同时做这两件事，相当于让外科医生边找手术工具边做手术。

解决方案：FastContext 把这两个阶段分离：用一个专门训练的轻量级"探索模型"（exploration model）先定位相关文件和上下文，再把精准的上下文交给代码生成模型。探索模型经过专门的训练，对"哪些文件与当前任务相关"有更强的判断力，减少了生成阶段需要处理的无关内容。

价值：相比混合架构，FastContext 在降低 token 消耗的同时提升了代码任务解题成功率，为大规模企业代码库的 Agent 部署提供了可行的效率路径。

未来方向："探索与生成分离"的 Agent 架构将成为大型代码库 AI 工具的标准模式，类似于搜索引擎中"检索"与"排序"模块的分工。

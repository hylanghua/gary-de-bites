Anthropic 逾 $3 亿收购 Stainless，竞品 SDK 工具链断供

Stainless 是 OpenAI、Google、Cloudflare 均在使用的 SDK 自动生成平台，能将 API 规格转换为 TypeScript、Python、Go、Java 等多语言 SDK 及 MCP 服务器（即让开发者和 agent 调用 API 的连接层）。Anthropic 宣布收购后，将关停所有托管服务。受影响的客户仍保留此前生成的 SDK 所有权和修改权，但未来无法继续使用平台服务。对竞争对手而言，他们正在使用的工具链实际上被断供了——Anthropic 此举既是把核心 SDK 研发能力内化，也间接给对手增加了基础设施迁移成本。

AI 方向观点

Ben Bites：模型越强，harness（运行框架）的角色越要转变

Ben Cawley 在今日 Ben's Bites 中写道：当模型足够强，harness 的重要性会下降——但他认为今天还没到那一天。不过转变的方向已经清晰：harness 的职责将从"管理用哪些工具、系统提示怎么写、上下文怎么管理"，向"管理 agent、沙箱（隔离的代码运行环境）、云端/本地资源调度"迁移。

他还提到自己现在的手机端 agent 使用习惯：Claude Code 的 /remote-control、Telegram bot、Droid 的移动端——但大多数时候用手机是在"头脑风暴"而非"构建"。他之前每天都在用 OpenClaw bot，但几周没说话了，原因是他现在专注于做一件主要的事：一本关于"如何思考和引导 agent"的参考手册。

harness 不会消失，它在等一次职责重组——从工具管理者变成 agent 的基础设施层。 Ben's Bites

Peter Yang（Roblox 产品负责人）：拆解 Anthropic 的五个构建维度

Peter Yang 今日发长推，深度分析 Anthropic 的模型构建方法，列出五个值得关注的维度：模型与 harness 的耦合设计（Claude 的能力边界和部署框架不是分开设计的）；agent"做梦"——让 agent 在非激活状态下也持续处理信息；evaluation 方法论（benchmark 怎么选、怎么防止过拟合）；意识研究（Anthropic 确实在认真对待模型的主观体验问题）；以及用写作文化作为 context 层——团队的书面沟通本身构成了模型训练的隐性基础设施。

Anthropic 把组织文化本身当成了 AI 系统的一部分，这和大多数 AI 公司的想法不一样。 X @petergyang

Aaron Levie（Box CEO）：Agent 成功的关键是"恰当约束的上下文"，不是越多越好

Levie 今日在 X 发布延伸分析：让 agent 完成任务的前提，不是给它堆砌更多工具和数据，而是给出"恰到好处的约束上下文"——精确划定边界、提供结构化的数据环境。他认为 agent 的成败，很大程度上取决于上游的数据策略是否到位。

实际含义对产品/企业团队而言：在把 agent 接入工作流之前，先要搞清楚哪些数据该暴露、哪些不该，结构化到什么程度，边界划在哪里——这些决策早于 agent 选型。

Agent 工程的真正门槛在于数据治理，而不是模型选型。 X @levie

Every（Dan Shipper）：100-agent 软件工厂里实际在发生什么

Every 今日 newsletter 主题是"Inside the 100-agent Software Factory"。Dan Shipper 分享了 Every 完全转向 agent 原生架构之后的复合工程（compound engineering）实践：传统软件是"写代码定义发生什么"，而 agent 原生软件是"用自然语言定义结果，让 agent 决定怎么实现"。Every 内部现在所有新功能都是 Claude Code 的调用封装，每个按钮背后是一个 agent 的 prompt 链路。

他还提到一个 Gas City 的迷你 vibe check，以及 Grok 的 X 草稿质量评分器——后者作为"写作 co-pilot"颇有意思：在你发出去之前，先帮你给自己打分。

agent 原生架构不是一个技术选择，是一个关于"谁在写代码"的组织决策。 Every
产品与商业

纯银（Vol.20260519）：滴滴 AI 打车不蠢，但场景太窄

纯银在英国旅行期间看到大 V 吐槽滴滴 AI 打车，回国自己用了之后写下这篇分析。结论：没有吐槽得那么蠢，但场景确实很窄。AI 打车的最大公约数是"选车"，本质是把高级搜索功能下放给普通用户——"空气清新"、"最近的车"、"后排宽敞"这类筛选项，AI 语义理解做起来顺手，降低使用门槛，提高撮合率。

但核心问题是：主路径叫车点一次，AI 打车要点三次，还需要集中注意力筛选信息——如果对筛选项不是强需求，就完全想不起来进这个入口。而真正是强需求、高渗透率的筛选项，早就内嵌到主路径去了。其他功能（找附近的店、预约叫车、订单查询）拼在一起心智混乱、场景低频。纯银总结：这是有意义的探索，目的是"回收市场反馈"，而非当下就打造一个高价值功能。相比之下，大众点评的"问点仔"和携程的"AI 问道"更糟糕，是大厂产品力下降的注脚。

AI 功能一旦脱离主路径，用户不是觉得它难用，而是根本不会想起来它存在。 小报童 · 纯银

AI 进展

ComplexMCP：首个大规模 MCP 工具沙箱基准，顶级模型通过率不超 60%

现状：现有 LLM agent benchmark 大多测试的是单独的、相互独立的 API 调用，与真实部署场景差距很大。

问题：现实中，工具之间存在状态依赖和交叉影响——上一步操作的结果会影响下一步可用的工具，API 也可能随机失败。目前没有基准能系统评估这种动态环境下的 agent 能力。

解决方案：ComplexMCP 在 MCP（模型上下文协议，即 agent 调用外部工具的标准接口）上构建基准，提供超过 300 个工具，来自 7 个有状态沙箱（覆盖 office 套件到金融系统）。通过种子驱动的架构模拟动态环境状态和随机 API 失败，同时保证测试可复现。

价值：揭示了当前模型在复杂工具环境中的真实短板：即便是顶级模型，在完整上下文和 RAG（检索增强生成）两种模式下，成功率均低于 60%。

未来方向：对于产品团队来说，这意味着在让 agent 接管多步骤工作流之前，需要认真评估工具的依赖复杂度，而非仅测试单步调用准确性。

HuggingFace · arXiv 2605.10787

多 Agent 推理预测图：如何选对通信拓扑（chain/star/mesh）

现状：在多 agent 系统中，开发者需要选择 agent 之间的通信拓扑——是链式（chain，顺序传递）、星型（star，中枢汇聚）还是网状（mesh，全连接），这个选择直接影响性能，但目前缺乏理论框架。

问题：不同任务的最优拓扑不同，盲目选择会导致通信开销过大或信息丢失。

解决方案：论文提出基于后继表示谱（successor-representation spectrum）的预测图框架，将推理任务的结构特征映射到最优通信拓扑，给出可解释的选择依据。

价值：为多 agent 系统的架构决策提供了一套可操作的分析工具，不再是试错。

未来方向：随着 agent 系统从单 agent 走向多 agent 协同，这类"拓扑选择框架"将成为 agent 基础设施设计的基础组件。

arXiv 2605.11453

ExploitBench：LLM 网络安全能力梯级基准，16 个阶段从漏洞发现到代码执行

现状：LLM 在网络安全领域的能力评估缺乏精细化分级，"会不会找漏洞"是个粗粒度标签，无法指导实际应用决策。

问题：安全漏洞的利用是一个多阶段链条，不同阶段对模型能力的要求差异很大，笼统评估掩盖了真实能力边界。

解决方案：ExploitBench 将利用能力分解为 16 个可测量的"能力标志"（flag，借用 CTF 夺旗赛概念），从覆盖分析、崩溃复现，经由沙箱原语、任意读写、控制流劫持，直到任意代码执行，形成能力阶梯（capability ladder）。

价值：帮助安全研究者和红队精确定位当前模型的能力上限，指导人机协同的安全测试策略。

未来方向：Cloudflare 测试 Mythos 时已发现"模型擅长找真实攻击链，但单模型+弱 harness 仍有大量漏网"，ExploitBench 这类基准正是量化这个差距的基础设施。

arXiv 2605.14153

EnergyAgentBench：首个基于实时电力市场数据的 agent 基准

现状：现有 agent benchmark 大多使用静态或合成数据，无法测试 agent 在动态、高频更新的真实环境中的决策能力。

问题：电力基础设施的运营决策（数据中心选址、电网调度）涉及实时价格信号和复杂约束，是一个典型的"需要 agent 但没有好基准"的场景。

解决方案：EnergyAgentBench 接入实时电力市场数据，设计 70 个任务变体，覆盖 5 个任务族，包括数据中心选址优化和电网管理。

价值：首次把 agent 能力测试锚定到实时数据流，填补了高价值行业场景的评估空白。

未来方向：随着 AI 数据中心能耗占比持续上升，能源管理 agent 将是未来几年基础设施团队的重要工具。

arXiv 2605.15230

MultiBreak：可扩展多轮越狱安全基准，覆盖多样化对抗场景

现状：现有越狱（jailbreak，绕过模型安全限制）测试多数是单轮攻击，而真实世界的攻击者越来越多地采用多轮渐进策略，单轮测试无法评估模型的真实安全边界。

问题：多轮越狱的测试用例生成困难，难以保证覆盖度和多样性，现有基准既不可扩展也不够全面。

解决方案：MultiBreak 提出可扩展的多轮越狱生成协议，自动构建多样化的多轮攻击序列，覆盖不同角色扮演、逐步诱导等对抗策略。

价值：为模型安全团队提供了更贴近真实攻击的评估工具，帮助识别单轮测试无法发现的安全漏洞。

未来方向：随着 agent 具备更长的会话记忆和多轮推理能力，多轮安全测试将成为模型发布前的标准检查项。
